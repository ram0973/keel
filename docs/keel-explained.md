# Keel — что это за язык, простыми словами

Этот текст для тех, кто знает C (или что-то похожее) и хочет понять, зачем
придумывать новый язык. Никаких терминов вроде «линейный тип» или «аффинный
тип» здесь не понадобится — только проблема, решение и примеры кода.

---

## 1. Проблема, ради которой всё затевалось

В C есть одна большая беда, которую он не признаёт: **язык не следит за тем,
кто за что отвечает**. Напишите на C программу, которая освобождает память, —
и компилятор не заметит, если вы обратитесь к освобождённой памяти позже.
Программа скомпилируется, запустится и будет работать нормально. А иногда
не будет — и упадёт через три дня на продакшене, в пятницу вечером, при
конкретном запросе пользователя.

Rust эту проблему решил. Но решил так, что теперь страдает программист.
Смотрите, как это выглядит.

```rust
struct Entity { hp: i32 }
struct World { entities: Vec<Entity> }

// Хотим: пошагать по сущности, зная о мире.
fn step(world: &mut World, entity: &mut Entity) {
    entity.advance();
    let collision = world.get_collision_for_entity(entity);
    //                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    // ОШИБКА: world уже заимствован изменяемо через entity.
    // entity взята ИЗ world — компилятор не различает «взять из» и «отдельно».
    entity.resolve(collision);
}
```

Rust не разделяет эти два случая. `entity` — ссылка на элемент внутри `world`,
и пока она жива, `world` целиком «занят». Чтобы обойти это, есть три пути, и
все три неприятны.

**Путь 1: передавать индекс и каждый раз перезапрашивать ссылку.**

```rust
fn step(world: &mut World, entity_id: usize) {
    let entity_mut = &mut world.entities[entity_id]; // проверка границ
    entity_mut.advance();
    let entity_read = &world.entities[entity_id];    // снова проверка границ
    let collision = world.get_collision_for_entity(entity_read);
    let entity_mut = &mut world.entities[entity_id]; // и снова
    entity_mut.resolve(collision);
}
```

Три раза перезапрашиваем, три проверки границ, и логика программы перемешана
с техническим обходом ограничения. На настоящем проекте это превращается в
то, что программисты называют «борьбой с компилятором».

**Путь 2: прятаться в `Rc<RefCell<T>>`.** Обёртка, внутри которой в рантайме
считается, кто что занял. Если двое полезут в одновременно — программа
упадёт. То есть проблему «проверить заранее» мы заменили проблемой «упасть
потом».

**Путь 3: пометить структуры временем жизни.** Появляются `'a`, `<'brand>`,
`GhostToken`, которые надо таскать через каждую функцию и каждое поле.

Всё это — плата за то, что Rust запрещает две изменяемые ссылки на один
объект одновременно. Запрет разумный сам по себе, но он **слишком грубый**:
он не различает «две ссылки на один и тот же элемент» и «ссылка на элемент
внутри контейнера плюс ссылка на сам контейнер». Второй случай безопасен, и
запрещать его — чистая потеря.

## 2. Идея Keel: запрещать не лишние ссылки, а только опасные

Rust спрашивает «не мешают ли эти две ссылки друг другу?». Keel спрашивает
«не умрёт ли то, на что они указывают, пока они живые?».

Это разные вопросы, и второй — тот, который действительно важен для
безопасности памяти. Ответ на первый «мешают» запрещает кучу полезного кода.
Ответ на второй ловит ровно те случаи, которые ломают программу.

Отсюда всё остальное отличается от Rust.

## 3. Как выглядит Keel

```keel
struct Entity { hp int; }
struct World { entities Vec<Entity>; }

fn step(world &World, entity in world.entities[] mut) {
    entity.advance();
    let collision = world.get_collision_for_entity(entity);
    entity.resolve(collision);
}
```

Сравните с Rust-версией выше. Различия:

- **Нет `'a`, `<'brand>`, `GhostToken`.** Нигде. Вообще.
- **Нет перезапроса ссылки.** `entity` — это `entity`, а не
  `&mut world.entities[entity_id]`, который надо доставать заново.
- **Нет проверок границ**, которые добавляются из-за того, что мы ходим по
  индексу.
- **Один вид ссылки** вместо `&` и `&mut`.

Ключевая часть — `entity in world.entities[] mut`. Читается как: «`entity`
указывает на один из элементов `world.entities`, и мы можем его менять».

Программист не пишет это руками в обычном коде — компилятель сам понимает,
что `entity` пришёл из `world.entities`. Это написано только в сигнатуре
функции, потому что внутри функции тело уже всё объясняет.

## 4. Что Keel умеет, а Rust — нет

**Две изменяемые ссылки на элементы одной коллекции.** В Rust это
запрещено, даже если элементы заведомо разные:

```rust
// Rust: ошибка E0499 — нельзя заимствовать entities дважды изменяемо
attack(&mut entities[0], &mut entities[1]);
```

В Keel — нормальный код. Это тот случай, где в Rust приходится брать
`split_at_mut` (работает не всегда) или городить таблицу ID.

**Ссылка на элемент плюс ссылка на контейнер.** Это и есть пример из раздела
1: `entity` и `world` указывают на разные вещи — на элемент и на контейнер,
и они не мешают друг другу, потому что элемент живёт не дольше контейнера,
а компилятор это знает.

**Несколько ссылок на один объект, все пишущие.** В Rust нельзя иметь две
`&mut` на одно и то же. В Keel — можно, пока объект жив:

```keel
let list = Vec<int>.new();
let a = &list;
let b = &list;
a.push(42);
b.push(73);   // Rust бы запретил
```

## 5. Что Keel умеет не хуже Rust

Keel не «слабее Rust». Всё, что Rust гарантирует по памяти, Keel гарантирует
тоже, плюс ещё кое-что.

**Память освобождается автоматически.** Значение, которое больше не нужно,
уничтожается само — не в конце блока, а сразу после последнего использования.
Это не только экономия памяти: мёртвое значение перестаёт «занимать» ссылку,
и конфликтов становится меньше. Отдельно можно указать `drop(x)`, если момент
освобождения важен по логике программы.

**Ошибки ловятся при компиляции.** Use-after-free, забытый `free`, двойное
освобождение — всё это ошибки компиляции, а не падения в проде.

**Нет мусора в рантайме.** Никакого GC, никакой паузы в случайный момент.
Память освобождается ровно тогда, когда значение стало не нужно.

**Нет null.** Значение либо есть, либо его нет — и «нет» выражается типом
`Option<T>`, а не падением в случайном месте.

**Нет «висячих» указателей.** Если указатель на то, что уже уничтожено, —
это ошибка компиляции.

## 6. Чем приходится платить

Честный раздел. Keel не бесплатный.

**Ссылки нельзя хранить в структурах.** Поле структуры не может содержать
ссылку — на первом этапе. Если нужно связать объекты, которые живут долго,
используется индекс или номер (ссылка на объект по номеру в таблице).
Это ровно тот компромисс, из-за которого Rust-игры ушли в ECS. Для веб-сервера
обычно терпимо: обработка запроса живёт в пределах одной функции, а долгоживущее
состояние (кэш, сессии) держится в таблицах.

**Точность требует указаний.** Если функция меняет объект целиком, всё внутри
него «считается затронутым», даже если она трогает одно поле из двадцати.
Чтобы этого избежать, в сигнатуре указывается, что именно меняется:

```keel
fn step(world &World, entity in world.entities[] mut)   // точечно
fn reset(world &World) mut(world)                        // целиком
```

Первый вариант даёт меньше ложных ошибок, второй — проще. Это компромисс
между точностью и простотой синтаксиса, и он неустраним.

**Внутри одной функции.** Проверка заимствований работает в пределах функции.
Связи между объектами, живущими дольше, выражаются иначе (см. выше).

**Диагностика ошибок — это отдельная работа.** Если ссылка стала недействительной
глубоко в цепочке вызовов, компилятор должен показать всю цепочку. Rust
потратил на это годы. Keel придётся потратить столько же, иначе «простой
синтаксис» обернётся непостижимыми сообщениями об ошибках.

**Модель новая и не проверенная.** Идеи, на которых стоит Keel, существуют
пока только в черновиках и экспериментальных реализациях. Дыры в них будут
обнаруживаться по ходу дела — это цена, которую платят все, кто делает новый
язык.

**Нет экосистемы.** Ни стандартной библиотеки, ни пакетов, ни HTTP-клиента.
Это не особенность дизайна, а особенность любого нового языка: сначала язык,
потом всё остальное.

## 7. Чего Keel НЕ делает

Чтобы не было недоразумений:

- **Не заменяет Rust.** Rust — язык системного программирования с
  гарантиями, за которые стоит бороться. Keel — прикладной язык: веб-серверы,
  утилиты, скрипты. Там, где нужна предсказуемость в каждом такте, Rust
  останется лучшим выбором.
- **Не быстрее Rust в рантайме.** Скорость компиляции — да, за счёт отказа от
  тяжёлых оптимизаций. Скорость работы программы — примерно как у C, не как
  у оптимизированного Rust.
- **Не решает задачу за вас.** Если вы держите разделяемое изменяемое
  состояние между потоками — это по-прежнему надо проектировать.

## 8. Как это соотносится с C, V и Rust

| | C | V | Rust | Keel |
|---|---|---|---|---|
| Безопасность памяти | нет | частично | да | да (в разработке) |
| Скорость компиляции | максимальная | максимальная | низкая | высокая |
| Скорость кода | высокая | высокая | высокая | высокая |
| Сложность заимствования | нет проверок | нет | высокая | низкая |
| Null | есть | нет | нет | нет |
| GC | нет | опционально | нет | нет |

V — ближайший родственник по духу (быстрый, простой, C-подобный), но его
безопасность держится на запрете null и неявной иммутабельности, а не на
проверке владения. Rust — ближайший по строгости, но платит за это сложностью
синтаксиса. Keel пытается взять строгость Rust и синтаксис C.

## 9. Итог в одном абзаце

Keel — это C-подобный язык, в котором компилятор знает, кому принадлежит
каждый кусок памяти, и поэтому может поймать ошибку «использовано после
освобождения» ещё до запуска программы. Плата за это — пара отступов в
сигнатурах функций. Награда — код, который пишется как на C, но не может
упасть из-за указателей.

Если вы писали на Rust и устали от того, что компилятор запрещает заведомо
безопасные вещи, — вот чем это лечится. Если вы писали на C и ни разу не
ловили use-after-free — вы в восторге, и вам это не нужно.
