# Keel — дизайн языка

Имя: Keel (киль). Киль — скрытый силовой элемент, который не даёт корпусу
разъехаться. Здесь ту же роль играет проверка владения: её почти не видно в
коде, но без неё программа не собирается.

## Стратегия

Простой синтаксис, безопасность памяти, быстрая компиляция в разработке —
в ущерб производительности рантайма, если придётся выбирать. Все три цели
ранжированы именно так: сначала чтобы код читался как C, потом чтобы
use-after-free был невозможен, потом чтобы dev-сборка была быстрой.
Современные идеи (group borrowing, generational references, region borrowing,
обратный safety check, ASAP-дроп) берутся, только если не ломают этот порядок.
Идея, которая требует аннотаций в каждом файле или тяжёлого анализа,
откладывается, а не упрощается молча.

Цель применения: прикладной код (веб-серверы, утилиты). Компиляция заметно
быстрее rustc; производительность рантайма вторична.

Источники идей: Valen (group borrowing, Evan Ovadia / Nick Smith), Vale
(generational references, region borrowing), «Making C++ Memory-Safe»
(borrowless affine style). Ссылки — в конце.

## 1. Что берём из источников

### 1.1 Group borrowing (Valen) — ядро модели

Пять механизмов, дословно из статьи:

1. Каждый объект описывается **путём** согласно single ownership
   (`world.entities[]`, `ship.engine`).
2. Каждая ссылка **помнит путь**, на который указывает. Тип ссылки —
   `&T in <path>`, а не `&T` с lifetime.
3. Уничтожение объекта делает неиспользуемыми все ссылки, указывающие
   *внутрь* его пути.
4. Сигнатура функции описывает, **какие пути она модифицирует** (`mut(self)`),
   и это часть функции, а не типа параметра.
5. Вызов функции инвалидирует всё, что указывает *внутрь* модифицированных путей.

Ключевое послабление относительно Rust: **shared-xor-mutable заменяется на
no-use-after-free**. Несколько ссылок на один объект могут одновременно
писать через него — это безопасно, пока никто не уничтожает объект под ними.
Пример, который Rust отвергает, а group borrowing принимает:

```
let list = Vec<int>.new();
let a = &list;
let b = &list;
a.push(42);   // обе ссылки указывают НА list, не ВНУТРЬ — валидны
b.push(73);
```

А вот ссылка внутрь коллекции инвалидируется мутацией контейнера:

```
let e = &vec[0];   // путь: vec[]
vec.push(...);     // модифицирует vec → всё внутри vec инвалидировано
e.fuel;            // ошибка компиляции
```

Следствия, которые мы принимаем как фичи:

- **Один вид ссылки**, не два. `mut` — не часть типа, а аннотация функции
  («эта функция модифицирует такие-то пути»). Это убирает раскол `&`/`&mut`
  и каскад переписываний сигнатур.
- **Точная инвалидация по путям** даёт «mutable-in-immutable»: функция может
  модифицировать `world.entities[]`, не инвалидируя ссылки на сам `world`.
  Это и безопаснее (API не даёт трогать лишнее), и дружелюбнее оптимизатору.
- **Type-stability exception**: модификация объекта не инвалидирует ссылки на
  его type-stable части (примитивы, struct-поля, массивы фиксированного
  размера). `vec.push` не инвалидирует ссылку на `vec.len`.

### 1.2 Borrowless affine style — фундамент, на котором всё стоит

Из «Making C++ Memory-Safe»: single ownership + move-семантика сами по себе
уже дают память-безопасность, без каких-либо ссылок вообще. Правила:

- Каждый объект имеет ровно одного владельца (стек, поле, коллекция).
- После move переменная не используется (проверяется статически).
- Ссылки — надстройка над этим фундаментом, а не его замена.

Практический вывод для v0: язык обязан быть корректным даже в подмножестве
без ссылок (передача владением, возврат владением, индексы вместо указателей
в полях структур). Ссылки добавляются вторым слоем.

### 1.3 Generational references — escape hatch, не основа

Group borrowing не выражает произвольные графы объектов (циклы, наблюдатели,
ссылки, живущие дольше области видимости). Vale решает это generational
references: ссылка хранит поколение объекта, разыменование проверяет его в
рантайме и возвращает option. Это не zero-cost, но для веб-сервера цена
пренебрежима.

Решение: generational reference (`Gen<T>` / `Weak<T>`) — явный тип в
стандартной библиотеке для случаев, где статический анализ не справляется.
Пользователь выбирает: статическая ссылка (бесплатно, ограничения) или
generational (рантайм-проверка, свобода). Язык не прячет этот выбор.

### 1.4 Reverse safety checking — алгоритм, не фича

Компилятор Valen проверяет безопасность функции **от конца к началу**:
использование ссылки порождает требование «она должна быть валидна здесь»,
которое протягивается назад до точки инвалидации или до начала функции.
Мотивы: удобство (требования текут к своим источникам), циклы (обратный
обход естественно обрабатывает обратные рёбра), скорость. Принимаем как
способ реализации, на семантику языка не влияет.

Четыре фазы компиляции функции (как в Valen): parse → typing →
grouping (каждая ссылка получает путь) → safety check (обратный обход).

## 2. Синтаксис (грамматика v0)

**Полная грамматика вынесена в отдельный документ: `keel-syntax.md`** —
там лексика, объявления, типы, выражения, таблица отличий от C и Rust,
примеры и список открытых вопросов.

Краткая сводка: C-подобный синтаксис, тип пишется после имени (`fuel int`,
как в Valen), нет `->` (авто-разыменование), нет объявлений в стиле C
(`int *x`), иммутабельность по умолчанию, `mut` — единственное слово
для изменяемости.

Три понятия, которые нельзя путать (подробно в п. 2.5.1 файла грамматики):

1. `let mut x` — можно переприсваивать саму переменную;
2. `&T` — ссылка, через которую **можно писать** (это и есть послабление
   group borrowing: несколько ссылок на один объект пишут одновременно);
3. `mut` в сигнатуре — **декларация** «эта функция меняет содержимое таких-то
   путей»; нужна вызывающему, чтобы инвалидировать его ссылки. Не система
   прав.

```keel
struct Entity { hp int; }
struct World { entities Vec<Entity>; }

fn step(world &World, entity in world.entities[] mut) {
    entity.advance();
    let collision = world.get_collision_for_entity(entity);
    entity.resolve(collision);
}

fn main() int {
    let mut world = World(Vec<Entity>.new());
    world.entities.push(Entity(42));
    print(world.entities[0].hp);
    return 0;
}
```

## 3. Правила владения и заимствования

1. **Single ownership.** У каждого значения ровно один владелец. Присваивание
   и передача аргументом не-ссылочного типа — это move. Использование после
   move — ошибка компиляции.
2. **Ссылка помнит путь.** `&expr` создаёт ссылку с путём, вычисленным из
   `expr`. Путь — часть типа ссылки и выводится; писать его явно нужно только
   в сигнатурах, где компилятор не видит тело (`in world.entities[]`).
3. **Инвалидация внутрь, не на.** Модификация объекта по пути P инвалидирует
   ссылки, чей путь — строгий потомок P. Ссылка на сам P остаётся валидной.
   Исключение type-stability: потомки, чей тип не может измениться по форме
   (примитив, struct, фиксированный массив), не инвалидируются.
4. **`mut` описывает функцию.** `mut(path, ...)` в сигнатуре — контракт:
   функция может модифицировать эти пути и ничего вне них. Вызов
   инвалидирует у вызывающего ссылки внутрь соответствующих фактических путей.
   Без `mut` функция ничего не модифицирует (проверяется по телу).
5. **Один вид ссылки, но с временным сужением.** Нет деления на shared/unique
   как у типов. Несколько ссылок на один путь могут писать одновременно.
   Когда компилятор доказывает, что других живых ссылок на путь нет, ссылку
   можно сузить до уникальной (`uniq`) — это даёт оптимизатору noalias и
   нужно для границы с Rust, но это вывод компилятора, а не аннотация,
   которую пишет пользователь. Без доказательства сужения aliasing-гарантий
   нет; для прикладного кода приемлемо.
6. **Стабильность формы — общее правило, не частный случай.** Мутация делится
   на два вида: содержимого (форма данных не меняется, ссылки внутрь живы) и
   формы (переключение варианта union, переаллокация — ссылки внутрь
   умирают). Инвалидация из п. 3.3 срабатывает только на мутацию формы.
   Поэтому ссылка на `vec.len` переживает `push`, а ссылка на элемент — нет.
   То же правило распространяется на `Rc<T>`: мутация содержимого через
   разделяемую ссылку проверяется статически и не требует `RefCell` с
   паникой; мутация формы требует доказанной уникальности. Это принцип, на
   котором Ante совмещает подсчёт ссылок и borrow checking без рантайм-паник.
7. **Ссылки не хранятся в структурах (v0).** Поле структуры не может иметь
   ссылочный тип. Долгоживущие связи выражаются индексами/ID (как Rule 4 в
   affine style) или `Gen<T>` (п. 1.3). Это главное ограничение v0 и главный
   источник простоты проверки: все ссылки умирают в конце функции.
8. **Нет сырых указателей.** Адресная арифметика отсутствует. Единственные
   способы получить память — владение, ссылка, индекс, `Gen<T>`.
9. **Инициализация обязательна.** Нет null и неинициализированных значений.
   Отсутствие значения — `Option<T>`, ошибка — `Result<T, E>`.
10. **Дроп сразу после последнего использования, не в конце блока.**
   Компилятор вставляет деструктор на последнем использовании значения
   (liveness), а не на закрывающей скобке. Это короче, чем drop-at-end-of-scope
   в Rust и C++, и напрямую облегчает проверку: мёртвое значение уже не
   держит заимствование, поэтому ложных конфликтов меньше и не нужны
   искусственные блоки `{ }` ради раннего освобождения. Следствия:
   - порядок дропа определяется потоком данных, а не текстом блока. Если
     деструктор наблюдаем (закрыл сокет, отпустил лок), это поведение
     документируется как часть языка, а не как деталь реализации;
   - значение, захваченное ссылкой, живо, пока жива ссылка: последнее
     использование владельца не раньше последнего использования ссылки;
   - явный `drop(x);` остаётся для случая, когда момент освобождения — часть
     логики программы, а не следствие liveness.

## 4. Уточнения по итогам MVP (2026-11)

Реализация MVP (`/home/ra/keel`) заставила уточнить несколько правил.
Формулировки ниже заменяют более ранние в разделах 3 и 4.

### 4.1. «Право писать» и «область инвалидации» — разные вещи

Это главное уточнение. Раньше `mut` в сигнатуре описывался как «функция
меняет эти пути», и проверка прав записи и проверка инвалидации были
смешаны. Разделить их необходимо:

- **Право писать** отвечает на вопрос «можно ли выполнить эту запись?»
  Владелец пути определяет ответ: локальная переменная — по `let mut`,
  параметр — по mut-контракту.
- **Область инвалидации** отвечает на вопрос «что станет недействительным
  у вызывающего после вызова?». Это и есть mut-контракт.

Одна проверка на оба вопроса даёт либо слишком строгий язык (запрещено всё,
что не объявлено, включая обычную локальную запись), либо потерю
инвалидации. В MVP эти проверки разведены: `ctx.declared` используется для
контракта, владелец пути — для права записи.

### 4.2. Сегмент `[]` — шаблон

Путь `world.entities[]` является префиксом `world.entities[0].hp`.
Это позволяет объявлять контракт на уровне коллекции, не перечисляя
элементы, и совпадает с семантикой Valen, где `[]` обозначает группу
элементов.

### 4.3. Два вида инвалидации

- **Replace** — значение по пути заменено целиком (`x.f = v`): инвалидируются
  ссылки на сам путь и всё внутри него.
- **MutateInside** — содержимое изменено, объект на месте (`vec.push(..)`):
  инвалидируются только ссылки строго внутри.

### 4.4. Пути параметров символические

Путь параметра — имя параметра, а не локальный uid. Благодаря этому
контракт вызываемой функции переносится в пространство вызывающего через
аргументы: `mut(world.entities[])` внутри функции становится путём
вызывающего при вызове. Это и есть межпроцедурная часть проверки.

### 4.5. Детерминированность обязательна

Первая версия проверщика искала владельца пути обходом `HashMap` и
выдавала разные результаты при разном seed. Ошибка проявилась только
потому, что тесты гонялись в двух окружениях. Правило: любой выбор
«один из нескольких равноправных» должен разбиваться по `uid`, а не по
порядку обхода.

### 4.6. Что показала реализация

Работает: замена значения объекта инвалидирует ссылки внутрь него;
несколько изменяемых ссылок на элементы одной коллекции разрешены;
ссылка на элемент и ссылка на контейнер сосуществуют; забытый `move`
ловится; неизменяемость ловится.

Не работает пока: ссылки в полях структур (нужны регионы), обобщённые
типы, `Vec`, generational references, Higher RAII.

Требует отдельной работы: точность контракта (грубый `mut(world.entities[])`
против точного `mut(world.entities[0])`), диагностика ошибок (пока
перечисляет пути, а не показывает цепочку инвалидации), поддержка
циклов (тело цикла проверяется двумя проходами — грубо, но ловит
использование после инвалидации в следующей итерации).

## 5. Что запрещено (и почему)

| Запрет | Причина |
|---|---|
| Ссылочные поля структур (v0) | Иначе нужны lifetimes или регионы; индексы и `Gen<T>` покрывают практику |
| Хранение ссылки дольше функции, где она создана | Следствие предыдущего; проверка становится внутрипроцедурной |
| Использование после move | Single ownership (п. 3.1) |
| Разыменование инвалидированной ссылки | Ядро безопасности (п. 3.3–3.4) |
| `mut`-аннотация шире фактического тела функции | Контракт должен быть точным, иначе инвалидация у вызывающих ложная |
| Сырые указатели, address-of с арифметикой | Дыра, которую статический анализ не закрывает |
| Null / неинициализированные переменные | Источник UB, заменяется Option |
| Гонки данных через разделяемую мутабельность между потоками (v0) | Модель безопасна в одном потоке; межпоточная передача — только владением. Разделяемая память между потоками — отдельная фича (region borrowing / scramble поколений), не v0 |
| Циклические структуры владения | Single ownership их не допускает; циклы — через индексы или `Gen<T>` |

## 6. Модель компиляции

- Фронтенд: лексер → парсер (рекурсивный спуск) → AST.
- Проходы на функцию: typing → grouping (присвоение путей ссылкам) →
  safety check обратным обходом (п. 1.4) → проверка move (прямым обходом).
- Бэкенд v0: генерация C, сборка `tcc` для dev-сборок и `clang -O2` для
  релиза. Обоснование: проверенный путь (так устроен V), даёт скорость
  компиляции без написания собственного кодогенератора, и читаемый вывод
  для отладки компилятора. Ссылки компилируются в обычные указатели —
  вся безопасность доказана статически, рантайм-проверок нет
  (кроме bounds-check массивов и `Gen<T>`).
- Дроп: вставка деструкторов по liveness, сразу после последнего
  использования (п. 3.10), а не на границе блока.

Ожидаемая скорость компиляции: фронтенд плюс tcc — на порядок быстрее rustc
на сопоставимом коде, потому что нет LLVM-оптимизаций и анализ
внутрипроцедурный (п. 4, строка 2). Это осознанный обмен: межпроцедурные
ссылки (хранящиеся в структурах) не выразимы до появления регионов.

## 7. Вне v0 (осознанно отложено)

- Ссылки в полях структур через регионы (region borrowing из Vale) —
  естественное расширение путей за пределы функции.
- `Gen<T>` / generational references как библиотечный тип.
- Временная уникальность для FFI с Rust (`&mut`-граница).
- Потокобезопасность разделяемых данных (scramble поколений, region borrowing).
- Дженерики за пределами простейших коллекций, трейты/интерфейсы.
- Модули, пакетный менеджер, стандартная библиотека сокетов.
- **Лёгкий интероп с C — наоборот, фича v0, не отложенное.** Поскольку бэкенд
  и так генерирует C, граница с C почти бесплатна: `extern "C"` функция
  вызывается как обычная, без обвязки и без отдельного FFI-слоя. Это закрывает
  пункт 6 из списка рисков: горячий участок, которому нужен `restrict` или
  ручная оптимизация, пишется на C и линкуется, не таща LLVM в основной путь.
  Правила границы: указатели, пришедшие из C, непроверяемы — они не получают
  путь и не участвуют в borrow checking; значение, отданное в C по указателю,
  считается заимствованным на время вызова и не может быть уничтожено или
  перемещено, пока вызов не вернулся. Безопасность памяти гарантируется по
  нашу сторону границы и никак не гарантируется по ту.
- **Higher RAII (линейные типы с именованными деструкторами), кандидат на v1.**
  Обычный RAII вызывает один неявный деструктор без аргументов — поэтому
  транзакцию нельзя выразить честно, только через флаг и молчаливый откат.
  Линейная структура обязана быть уничтожена явно и только разрешёнными
  функциями (`commit`/`rollback` принимают её по владению и уничтожают сами):
  забыть нельзя, уничтожить в обход нельзя. Даёт статические гарантии там, где
  `#[must_use]` обходится: согласованность кэша (токен, уничтожаемый только
  функцией удаления из кэша), обязательство завершить Future, неотменённое
  соединение, обязательный вызов колбэка. Строго сильнее и RAII, и `defer`.
  Ограничение: линейность заразна вверх — структура с линейным полем сама
  вынуждена быть линейной, это та же «раскраска функций», что у async. Поэтому
  только явным ключевым словом, никогда по умолчанию.
- Интероп с Rust глубже C ABI. Group borrowing задуман как надмножество
  borrow checker'а Rust и в принципе может проверять заимствования через
  границу, но путь Valen (встраивание rustc через нестабильный rustc_driver,
  совместная мономорфизация) противоречит скорости сборки. Если интероп
  понадобится — через обычный FFI. Важное следствие той же статьи: чужой IR,
  спроектированный под другую модель памяти (Rust MIR с уникальными
  изменяемыми ссылками), не годится как цель кодогенерации — это независимое
  подтверждение выбора «свой IR, генерация C».

Практическое следствие group borrowing, не отражённое выше: разделяемое
владение изменяемыми данными не требует рантайм-проверки. В Rust `Rc<T>`
нельзя мутировать без `RefCell` (паника при конфликте). Поскольку у нас
несколько ссылок и так могут писать в один объект, `Rc<T>` мутируется
напрямую — разделяемое состояние (кэш, пул соединений) без обёрток и паник.

### 7.1. Долги, найденные при написании прикладных примеров

Эти пробелы не были видны на тестах семантики и проявились только тогда,
когда появился код, похожий на настоящий.

- **Перемещение из элемента массива не ловится.** `book.entries[j] =
  book.entries[j + 1]` — это move из элемента коллекции, что в Rust запрещено
  (элемент остался бы «дырой»). Наш checker помечает перемещённым только
  простые переменные, поэтому такое выражение проходит. В рантайме сейчас
  это безопасно (значение копируется, деструкторов нет), но семантически
  дыра настоящая. Нужен запрет на move из не-владельческого места.
- **Групповая гранулярность путей элементов.** Ссылка на элемент коллекции
  указывает на группу `book.entries[]`, а не на конкретный индекс. Поэтому
  после сдвига записей (удаление) ссылка формально остаётся живой, хотя
  указывает уже на другую запись. Конкретный индекс пути (`Idx(0)`) спасает
  от этого лишь частично: при динамическом индексе путь снова становится
  групповым. Нужно либо различать пути элементов, либо честно объявить
  ссылку на элемент ссылкой на группу.
- **Коллизии имён со стандартной библиотекой.** Имена пользовательских
  функций попадали в C без преобразования, и любая функция, названная как
  функция libc (`remove` из stdio.h, `index` из strings.h), приводила к
  конфликту типов. Исправлено префиксом `k_` в бэкенде, но правило должно
  быть зафиксировано в языке: любое имя пользователя может совпасть с
  имением из libc, и это не должно быть ошибкой.
- **Локальная переменная может перекрыть функцию libc.** Если назвать
  локальную переменную `printf` или `strcmp`, сгенерированный C не соберётся
  либо соберётся неверно. Сейчас локальные имена не преобразуются — это
  сделано ради читаемости вывода C, и решение надо пересмотреть, когда
  появится стандартная библиотека.
- **Сравнение строк.** Раньше `==` для строк сравнивал указатели, а не
  содержимое. Исправлено (`strcmp`), но в языке не определено, как
  вообще должны вести себя строки: это значения или указатели на
  неизменяемые данные? От ответа зависит, нужны ли строковые литералы
  во владении.
- **Ошибки без Option/Result.** Любая функция, которая может не найти
  запись или не найти место, вынуждена возвращать `-1`/`0` и печатать
  сообщение сама. Это не масштабируется: нужен либо `Option`, либо
  `Result`, либо идиома возврата ошибки.
- **C-backend наследует неопределённое поведение C.** Сейчас Keel
  транслируется в C, и всё, что C не определяет, не определяется и в Keel:
  порядок вычисления аргументов (`f(a(), b())` — какой раньше?), поведение
  при переполнении `int`, что происходит с неинициализированной памятью.
  Язык, обещающий безопасность памяти, не может оставлять такие вещи
  неопределёнными — пользователь должен знать, что получит. Это главная
  причина, по которой C-backend не годится для продакшена.
- **Диагностика на границе с C.** Ошибки времени компиляции, приходящие от
  `cc`, приходят словами gcc: «declaration of 'empty' as array of voids».
  Для пользователя Keel это нечитаемо. Нужен слой, переводящий ошибки C в
  диагностику Keel с указанием строки исходника. Дёшево, но чинит только
  симптом.

### 7.2. Порядок работы над долгами

1. `Option`/`Result` и обработка ошибок — без этого прикладной код
   получается либо нечитаемым, либо полным `-1`.
2. Диагностика с цепочкой инвалидации (см. открытые вопросы в
   `keel-syntax.md`).
3. Запрет move из элемента массива.
4. Точность путей элементов коллекции.
5. Регионы для ссылок в полях структур.
6. **Переход на собственный IR (Cranelift)** — когда фронтенд устоится.
   Оценка миграции и измеренные цифры — в `docs/cranelift-experiment.md`.
   Пункт стоит последним не потому, что он менее важен, а потому, что
   до него фронтенд всё равно меняется: переписывать кодогенерацию
   дважды невыгодно. Отдельно проверено, что SSA-конструктор писать
   не придётся: `cranelift_frontend::SSABuilder` строит SSA-форму сам,
   достаточно скормить ему AST Keel.

### 7.3. Про C-backend и миграцию на Cranelift

Коротко, чтобы не искать по документу.

**Что мы имеем сейчас.** Keel → текст C → `cc` → машинный код. Текст C
генерирует мой кодогенератор, машинный код — gcc. Диагностика частично
моя (checker), частично gcc.

**Что даст Cranelift.** Свой IR, свой машинный код, своя диагностика,
своя семантика — вместо унаследованной от C. Цена — в ~4.5 раза больше
кода в кодогенераторе и необходимость строить SSA-форму самому.

**Почему не сейчас.** Эксперимент показал: полный цикл компиляции сейчас
занимает ~30 мс, из которых кодогенерация — около 30 мс, а фронтенд —
доли миллисекунды. Cranelift кодогенерирует за ~2 мс. То есть выигрыш в
скорости — десятки миллисекунд, а не порядок величины. Главный выигрыш
(своя семантика вместо неопределённого поведения C) нужен перед
продакшеном, а не во время проверки идеи.

**Что делаем вместо.** Пока фронтенд не устоялся — держим C-backend и
чиним его границы: переводим ошибки gcc в диагностику Keel. Это дёшево
и снимает самый неприятный симптом.

Полный эксперимент с кодом и замерами: `docs/cranelift-experiment.md`.
