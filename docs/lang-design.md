# Keel — дизайн языка

Имя: Keel (киль). Киль — скрытый силовой элемент, который не даёт корпусу
разъехаться. Здесь ту же роль играет проверка владения: её почти не видно в
коде, но без неё программа не собирается.

## Стратегия

Простой синтаксис, безопасность памяти, быстрая компиляция в разработке —
в ущерб производительности рантайма, если придётся выбирать. Все три цели
ранжированы именно так: сначала чтобы код читался как C, потом чтобы
use-after-free был невозможен, потом чтобы dev-сборка была быстрой.
Современные идеи (group borrowing, generational references, region borrowing,
обратный safety check, ASAP-дроп) берутся, только если не ломают этот порядок.
Идея, которая требует аннотаций в каждом файле или тяжёлого анализа,
откладывается, а не упрощается молча.

Цель применения: прикладной код (веб-серверы, утилиты). Компиляция заметно
быстрее rustc; производительность рантайма вторична.

Источники идей: Valen (group borrowing, Evan Ovadia / Nick Smith), Vale
(generational references, region borrowing), «Making C++ Memory-Safe»
(borrowless affine style). Ссылки — в конце.

## 1. Что берём из источников

### 1.1 Group borrowing (Valen) — ядро модели

Пять механизмов, дословно из статьи:

1. Каждый объект описывается **путём** согласно single ownership
   (`world.entities[]`, `ship.engine`).
2. Каждая ссылка **помнит путь**, на который указывает. Тип ссылки —
   `&T in <path>`, а не `&T` с lifetime.
3. Уничтожение объекта делает неиспользуемыми все ссылки, указывающие
   *внутрь* его пути.
4. Сигнатура функции описывает, **какие пути она модифицирует** (`mut(self)`),
   и это часть функции, а не типа параметра.
5. Вызов функции инвалидирует всё, что указывает *внутрь* модифицированных путей.

Ключевое послабление относительно Rust: **shared-xor-mutable заменяется на
no-use-after-free**. Несколько ссылок на один объект могут одновременно
писать через него — это безопасно, пока никто не уничтожает объект под ними.
Пример, который Rust отвергает, а group borrowing принимает:

```
let list = Vec<int>.new();
let a = &list;
let b = &list;
a.push(42);   // обе ссылки указывают НА list, не ВНУТРЬ — валидны
b.push(73);
```

А вот ссылка внутрь коллекции инвалидируется мутацией контейнера:

```
let e = &vec[0];   // путь: vec[]
vec.push(...);     // модифицирует vec → всё внутри vec инвалидировано
e.fuel;            // ошибка компиляции
```

Следствия, которые мы принимаем как фичи:

- **Один вид ссылки**, не два. `mut` — не часть типа, а аннотация функции
  («эта функция модифицирует такие-то пути»). Это убирает раскол `&`/`&mut`
  и каскад переписываний сигнатур.
- **Точная инвалидация по путям** даёт «mutable-in-immutable»: функция может
  модифицировать `world.entities[]`, не инвалидируя ссылки на сам `world`.
  Это и безопаснее (API не даёт трогать лишнее), и дружелюбнее оптимизатору.
- **Type-stability exception**: модификация объекта не инвалидирует ссылки на
  его type-stable части (примитивы, struct-поля, массивы фиксированного
  размера). `vec.push` не инвалидирует ссылку на `vec.len`.

### 1.2 Borrowless affine style — фундамент, на котором всё стоит

Из «Making C++ Memory-Safe»: single ownership + move-семантика сами по себе
уже дают память-безопасность, без каких-либо ссылок вообще. Правила:

- Каждый объект имеет ровно одного владельца (стек, поле, коллекция).
- После move переменная не используется (проверяется статически).
- Ссылки — надстройка над этим фундаментом, а не его замена.

Практический вывод для v0: язык обязан быть корректным даже в подмножестве
без ссылок (передача владением, возврат владением, индексы вместо указателей
в полях структур). Ссылки добавляются вторым слоем.

### 1.3 Generational references — escape hatch, не основа

Group borrowing не выражает произвольные графы объектов (циклы, наблюдатели,
ссылки, живущие дольше области видимости). Vale решает это generational
references: ссылка хранит поколение объекта, разыменование проверяет его в
рантайме и возвращает option. Это не zero-cost, но для веб-сервера цена
пренебрежима.

Решение: generational reference (`Gen<T>` / `Weak<T>`) — явный тип в
стандартной библиотеке для случаев, где статический анализ не справляется.
Пользователь выбирает: статическая ссылка (бесплатно, ограничения) или
generational (рантайм-проверка, свобода). Язык не прячет этот выбор.

### 1.4 Reverse safety checking — алгоритм, не фича

Компилятор Valen проверяет безопасность функции **от конца к началу**:
использование ссылки порождает требование «она должна быть валидна здесь»,
которое протягивается назад до точки инвалидации или до начала функции.
Мотивы: удобство (требования текут к своим источникам), циклы (обратный
обход естественно обрабатывает обратные рёбра), скорость. Принимаем как
способ реализации, на семантику языка не влияет.

Четыре фазы компиляции функции (как в Valen): parse → typing →
grouping (каждая ссылка получает путь) → safety check (обратный обход).

## 2. Синтаксис (грамматика v0)

**Полная грамматика вынесена в отдельный документ: `keel-syntax.md`** —
там лексика, объявления, типы, выражения, таблица отличий от C и Rust,
примеры и список открытых вопросов.

Краткая сводка: C-подобный синтаксис, тип пишется после имени (`fuel int`,
как в Valen), нет `->` (авто-разыменование), нет объявлений в стиле C
(`int *x`), иммутабельность по умолчанию, `mut` — единственное слово
для изменяемости.

Три понятия, которые нельзя путать (подробно в п. 2.5.3 файла грамматики):

1. `let mut x` — можно переприсваивать саму переменную;
2. `&T` — ссылка, через которую **можно писать** (это и есть послабление
   group borrowing: несколько ссылок на один объект пишут одновременно);
3. `mut` в сигнатуре — **декларация** «эта функция меняет содержимое таких-то
   путей»; нужна вызывающему, чтобы инвалидировать его ссылки. Не система
   прав.

```keel
struct Entity { hp int; }
struct World { entities Vec<Entity>; }

fn step(world &World, entity in world.entities[] mut) {
    entity.advance();
    let collision = world.get_collision_for_entity(entity);
    entity.resolve(collision);
}

fn main() int {
    let mut world = World(Vec<Entity>.new());
    world.entities.push(Entity(42));
    print(world.entities[0].hp);
    return 0;
}
```

## 3. Правила владения и заимствования

1. **Single ownership.** У каждого значения ровно один владелец. Присваивание
   и передача аргументом не-ссылочного типа — это move. Использование после
   move — ошибка компиляции.
2. **Ссылка помнит путь.** `&expr` создаёт ссылку с путём, вычисленным из
   `expr`. Путь — часть типа ссылки и выводится; писать его явно нужно только
   в сигнатурах, где компилятор не видит тело (`in world.entities[]`).
3. **Инвалидация внутрь, не на.** Модификация объекта по пути P инвалидирует
   ссылки, чей путь — строгий потомок P. Ссылка на сам P остаётся валидной.
   Исключение type-stability: потомки, чей тип не может измениться по форме
   (примитив, struct, фиксированный массив), не инвалидируются.
4. **`mut` описывает функцию.** `mut(path, ...)` в сигнатуре — контракт:
   функция может модифицировать эти пути и ничего вне них. Вызов
   инвалидирует у вызывающего ссылки внутрь соответствующих фактических путей.
   Без `mut` функция ничего не модифицирует (проверяется по телу).
5. **Один вид ссылки, но с временным сужением.** Нет деления на shared/unique
   как у типов. Несколько ссылок на один путь могут писать одновременно.
   Когда компилятор доказывает, что других живых ссылок на путь нет, ссылку
   можно сузить до уникальной (`uniq`) — это даёт оптимизатору noalias и
   нужно для границы с Rust, но это вывод компилятора, а не аннотация,
   которую пишет пользователь. Без доказательства сужения aliasing-гарантий
   нет; для прикладного кода приемлемо.
6. **Стабильность формы — общее правило, не частный случай.** Мутация делится
   на два вида: содержимого (форма данных не меняется, ссылки внутрь живы) и
   формы (переключение варианта union, переаллокация — ссылки внутрь
   умирают). Инвалидация из п. 3.3 срабатывает только на мутацию формы.
   Поэтому ссылка на `vec.len` переживает `push`, а ссылка на элемент — нет.
   То же правило распространяется на `Rc<T>`: мутация содержимого через
   разделяемую ссылку проверяется статически и не требует `RefCell` с
   паникой; мутация формы требует доказанной уникальности. Это принцип, на
   котором Ante совмещает подсчёт ссылок и borrow checking без рантайм-паник.
7. **Ссылки в полях структур: время жизни (не решено).** Поле структуры
   *может* иметь ссылочный тип — это проверено на компиляторе: поле
   объявляется, конструктор ссылку принимает, поле читается. Ограничение v0 —
не «нельзя иметь ссылочное поле», а «ссылка не должна пережить функцию»:
`return Holder(&i)` запрещено, потому что `i` умрёт вместе с кадром.
Проверка — анализ выхода (п. 6 раздела 7.2). Долгоживущие связи
выражаются индексами/ID (как Rule 4 в affine style) или `Gen<T>` (п. 1.3).
8. **Нет сырых указателей.** Адресная арифметика отсутствует. Единственные
   способы получить память — владение, ссылка, индекс, `Gen<T>`.
9. **Инициализация обязательна.** Нет null и неинициализированных значений.
   Отсутствие значения — `Option<T>`, ошибка — `Result<T, E>`.
10. **Дроп сразу после последнего использования, не в конце блока.**
   Компилятор вставляет деструктор на последнем использовании значения
   (liveness), а не на закрывающей скобке. Это короче, чем drop-at-end-of-scope
   в Rust и C++, и напрямую облегчает проверку: мёртвое значение уже не
   держит заимствование, поэтому ложных конфликтов меньше и не нужны
   искусственные блоки `{ }` ради раннего освобождения. Следствия:
   - порядок дропа определяется потоком данных, а не текстом блока. Если
     деструктор наблюдаем (закрыл сокет, отпустил лок), это поведение
     документируется как часть языка, а не как деталь реализации;
   - значение, захваченное ссылкой, живо, пока жива ссылка: последнее
     использование владельца не раньше последнего использования ссылки;
   - явный `drop(x);` остаётся для случая, когда момент освобождения — часть
     логики программы, а не следствие liveness.

## 4. Уточнения по итогам MVP (2026-11)

Реализация MVP (`/home/ra/keel`) заставила уточнить несколько правил.
Формулировки ниже заменяют более ранние в разделах 3 и 4.

### 4.1. «Право писать» и «область инвалидации» — разные вещи

Это главное уточнение. Раньше `mut` в сигнатуре описывался как «функция
меняет эти пути», и проверка прав записи и проверка инвалидации были
смешаны. Разделить их необходимо:

- **Право писать** отвечает на вопрос «можно ли выполнить эту запись?»
  Владелец пути определяет ответ: локальная переменная — по `let mut`,
  параметр — по mut-контракту.
- **Область инвалидации** отвечает на вопрос «что станет недействительным
  у вызывающего после вызова?». Это и есть mut-контракт.

Одна проверка на оба вопроса даёт либо слишком строгий язык (запрещено всё,
что не объявлено, включая обычную локальную запись), либо потерю
инвалидации. В MVP эти проверки разведены: `ctx.declared` используется для
контракта, владелец пути — для права записи.

### 4.2. Сегмент `[]` — шаблон

Путь `world.entities[]` является префиксом `world.entities[0].hp`.
Это позволяет объявлять контракт на уровне коллекции, не перечисляя
элементы, и совпадает с семантикой Valen, где `[]` обозначает группу
элементов.

### 4.3. Два вида инвалидации

- **Replace** — значение по пути заменено целиком (`x.f = v`): инвалидируются
  ссылки на сам путь и всё внутри него.
- **MutateInside** — содержимое изменено, объект на месте (`vec.push(..)`):
  инвалидируются только ссылки строго внутри.

### 4.3.1. Что именно запрещено (и что — нет)

Это стоит сказать прямо, потому что формулировка «запрещено не совпадение
ссылок» легко понимается неверно.

**Разрешено:**

| Разрешено | Почему |
|---|---|
| Две ссылки на **разные** элементы одной коллекции, обе живут одновременно | В Rust это E0499 (`cannot borrow as mutable more than once`). Ради этого всё и затевалось |
| Две ссылки на **один и тот же** объект | В Keel один вид ссылки (`&T`), и право писать определяется владельцем пути, а не видом ссылки. Запрета на совпадение ссылок нет |
| Запись через ссылку, если владелец пути — `mut` | Право писать — от владельца, не от вида ссылки |

**Запрещено (это и есть ядро безопасности):**

| Запрещено | Что ловится |
|---|---|
| Использование ссылки после **замены** объекта на её пути | `ссылка ... инвалидирована: объект ... был изменён или уничтожен` |
| Использование после **move** | `уже перемещён` |
| Запись в не-`mut` переменную или в путь без объявленного контракта | `не объявлен как mut` / `путь не объявлен изменяемым` |

**Чем Keel отличается от Rust.** Rust различает `&T` и `&mut T` и потому
запрещает две изменяемые ссылки на один объект. Keel такого различия не
делает: ссылка одна, а право писать даёт владелец пути. Поэтому:

- Keel **слабее** Rust в одном: две ссылки на один объект, обе пишущие,
  разрешены;
- Keel **сильнее** Rust в другом: две ссылки на разные элементы
  коллекции не требуют ни lifetime-аннотаций, ни перезапроса.

То есть Keel не «Rust с путями», а другая модель: безопасность через
**инвалидацию**, а не через исключительность. Проверено на компиляторе,
зафиксировано тестами `две_ссылки_на_один_объект_разрешены` и
`ссылка_на_заменённый_объект_ловится`.

### 4.4. Пути параметров символические

Путь параметра — имя параметра, а не локальный uid. Благодаря этому
контракт вызываемой функции переносится в пространство вызывающего через
аргументы: `mut(world.entities[])` внутри функции становится путём
вызывающего при вызове. Это и есть межпроцедурная часть проверки.

### 4.5. Детерминированность обязательна

Первая версия проверщика искала владельца пути обходом `HashMap` и
выдавала разные результаты при разном seed. Ошибка проявилась только
потому, что тесты гонялись в двух окружениях. Правило: любой выбор
«один из нескольких равноправных» должен разбиваться по `uid`, а не по
порядку обхода.

### 4.6. Что показала реализация

Работает: замена значения объекта инвалидирует ссылки внутрь него;
несколько изменяемых ссылок на элементы одной коллекции разрешены;
ссылка на элемент и ссылка на контейнер сосуществуют; забытый `move`
ловится; неизменяемость ловится.

Не работает пока: обобщённые типы, `Vec`, generational references, Higher RAII.

Работает: ссылка не может пережить функцию — анализ выхода закрывает
use-after-free через ссылку в поле структуры (п. 6 раздела 7.2).

Требует отдельной работы: точность контракта (грубый `mut(world.entities[])`
против точного `mut(world.entities[0])`), диагностика ошибок (пока
перечисляет пути, а не показывает цепочку инвалидации), поддержка
циклов (тело цикла проверяется двумя проходами — грубо, но ловит
использование после инвалидации в следующей итерации).

### 4.7. Что такое копируемое значение

`is_copy` определяет, отнимает ли передача владение. Копируются:

| Тип | Почему |
|---|---|
| `int`, `bool` | машинное слово, копия тривиальна |
| `string` | неизменяемая строка; копируется указатель, содержимое не меняется |
| `&T` | **ссылка — это указатель**: копирование не отнимает владение у оригинала |

Ссылка копируема, потому что заимствование не передаёт владение. Это
то же правило, что в Rust: `&T: Copy`, поэтому `let r2 = r1;` оставляет
обе ссылки живыми. Без этого пришлось бы писать `&r` на каждое
использование — шум без выигрыша в безопасности.

Структуры и массивы всегда перемещаются: копирование структуры
скрывало бы от читателя стоимость (у `Vec` это был бы `malloc`).

**Найденный баг:** до этого ссылка не входила в `is_copy`, и
`println(r); println(r);` давало «`r` уже перемещён». При этом
`f(r); f(r);` и `r.n` работали — то есть проверка была
непоследовательной. Исправлено: `Type::Ref(_)` добавлен в `is_copy`.

### 4.8. Вложенные массивы в C-бэкенде

В C размеры пишутся ПОСЛЕ имени: `int64_t a[2][2]`, а не
`int64_t[2] a[2]`. Поэтому декларатор строится рекурсивно — размер
дописывается к имени, а рекурсия уходит в тип элемента.

**Найденный баг:** генератор строил декларацию не рекурсивно, и
`[[int; 2]; 2]` давал невалидный C `int64_t[2] grid[2]`. Компилятор C
падал с `expected identifier or '(' before '[' token`. Исправлено:
`decl` и `array_items` рекурсивны, а для составного литерала добавлен
`array_literal_ty` (там размеры, наоборот, пишутся после типа:
`(int64_t[2][]){...}`).

## 5. Что запрещено (и почему)

| Запрет | Причина |
|---|---|
| Ссылка, уехавшая из функции | Ссылка не может жить дольше функции, где создана; проверка становится внутрипроцедурной. **Реализовано** — анализ выхода (п. 6 раздела 7.2) |
| Использование после move | Single ownership (п. 3.1) |
| Разыменование инвалидированной ссылки | Ядро безопасности (п. 3.3–3.4) |
| `mut`-аннотация шире фактического тела функции | Контракт должен быть точным, иначе инвалидация у вызывающих ложная |
| Сырые указатели, address-of с арифметикой | Дыра, которую статический анализ не закрывает |
| Null / неинициализированные переменные | Источник UB, заменяется Option |
| Гонки данных через разделяемую мутабельность между потоками (v0) | Модель безопасна в одном потоке; межпоточная передача — только владением. Разделяемая память между потоками — отдельная фича (region borrowing / scramble поколений), не v0 |
| Циклические структуры владения | Single ownership их не допускает; циклы — через индексы или `Gen<T>` |

## 6. Модель компиляции

- Фронтенд: лексер → парсер (рекурсивный спуск) → AST.
- Проходы на функцию: typing → grouping (присвоение путей ссылкам) →
  safety check обратным обходом (п. 1.4) → проверка move (прямым обходом).
- Бэкенд v0: генерация C, сборка `tcc` для dev-сборок и `clang -O2` для
  релиза. Обоснование: проверенный путь (так устроен V), даёт скорость
  компиляции без написания собственного кодогенератора, и читаемый вывод
  для отладки компилятора. Ссылки компилируются в обычные указатели —
  вся безопасность доказана статически, рантайм-проверок нет
  (кроме bounds-check массивов и `Gen<T>`).
- Дроп: вставка деструкторов по liveness, сразу после последнего
  использования (п. 3.10), а не на границе блока.

Ожидаемая скорость компиляции: фронтенд плюс tcc — на порядок быстрее rustc
на сопоставимом коде, потому что нет LLVM-оптимизаций и анализ
внутрипроцедурный (п. 4, строка 2). Это осознанный обмен: межпроцедурные
ссылки (хранящиеся в структурах) требуют отдельного механизма времени
жизни — см. п. 6 раздела 7.2.

## 7. Вне v0 (осознанно отложено)

- Ссылки в полях структур: время жизни. Ссылка в поле объявляется,
  принимается конструктором и читается, но не может пережить функцию —
  анализ выхода это проверяет (п. 6 раздела 7.2). Ссылка, живущая
  дольше функции, требует поколений (`Gen<T>`) и кучи.
- `Gen<T>` / generational references как библиотечный тип.
- Временная уникальность для FFI с Rust (`&mut`-граница).
- Потокобезопасность разделяемых данных (scramble поколений, region borrowing).
- Дженерики за пределами простейших коллекций, трейты/интерфейсы.
- Модули, пакетный менеджер, стандартная библиотека сокетов.
- **Лёгкий интероп с C — наоборот, фича v0, не отложенное.** Поскольку бэкенд
  и так генерирует C, граница с C почти бесплатна: `extern "C"` функция
  вызывается как обычная, без обвязки и без отдельного FFI-слоя. Это закрывает
  пункт 6 из списка рисков: горячий участок, которому нужен `restrict` или
  ручная оптимизация, пишется на C и линкуется, не таща LLVM в основной путь.
  Правила границы: указатели, пришедшие из C, непроверяемы — они не получают
  путь и не участвуют в borrow checking; значение, отданное в C по указателю,
  считается заимствованным на время вызова и не может быть уничтожено или
  перемещено, пока вызов не вернулся. Безопасность памяти гарантируется по
  нашу сторону границы и никак не гарантируется по ту.
- **Higher RAII (линейные типы с именованными деструкторами), кандидат на v1.**
  Обычный RAII вызывает один неявный деструктор без аргументов — поэтому
  транзакцию нельзя выразить честно, только через флаг и молчаливый откат.
  Линейная структура обязана быть уничтожена явно и только разрешёнными
  функциями (`commit`/`rollback` принимают её по владению и уничтожают сами):
  забыть нельзя, уничтожить в обход нельзя. Даёт статические гарантии там, где
  `#[must_use]` обходится: согласованность кэша (токен, уничтожаемый только
  функцией удаления из кэша), обязательство завершить Future, неотменённое
  соединение, обязательный вызов колбэка. Строго сильнее и RAII, и `defer`.
  Ограничение: линейность заразна вверх — структура с линейным полем сама
  вынуждена быть линейной, это та же «раскраска функций», что у async. Поэтому
  только явным ключевым словом, никогда по умолчанию.
- Интероп с Rust глубже C ABI. Group borrowing задуман как надмножество
  borrow checker'а Rust и в принципе может проверять заимствования через
  границу, но путь Valen (встраивание rustc через нестабильный rustc_driver,
  совместная мономорфизация) противоречит скорости сборки. Если интероп
  понадобится — через обычный FFI. Важное следствие той же статьи: чужой IR,
  спроектированный под другую модель памяти (Rust MIR с уникальными
  изменяемыми ссылками), не годится как цель кодогенерации — это независимое
  подтверждение выбора «свой IR, генерация C».

Практическое следствие group borrowing, не отражённое выше: разделяемое
владение изменяемыми данными не требует рантайм-проверки. В Rust `Rc<T>`
нельзя мутировать без `RefCell` (паника при конфликте). Поскольку у нас
несколько ссылок и так могут писать в один объект, `Rc<T>` мутируется
напрямую — разделяемое состояние (кэш, пул соединений) без обёрток и паник.

### 7.1. Долги, найденные при написании прикладных примеров

Эти пробелы не были видны на тестах семантики и проявились только тогда,
когда появился код, похожий на настоящий.

- **Перемещение из элемента массива не ловится.** `book.entries[j] =
  book.entries[j + 1]` — это move из элемента коллекции, что в Rust запрещено
  (элемент остался бы «дырой»). Наш checker помечает перемещённым только
  простые переменные, поэтому такое выражение проходит. В рантайме сейчас
  это безопасно (значение копируется, деструкторов нет), но семантически
  дыра настоящая. Нужен запрет на move из не-владельческого места.
- **Групповая гранулярность путей элементов.** Ссылка на элемент коллекции
  указывает на группу `book.entries[]`, а не на конкретный индекс. Поэтому
  после сдвига записей (удаление) ссылка формально остаётся живой, хотя
  указывает уже на другую запись. Конкретный индекс пути (`Idx(0)`) спасает
  от этого лишь частично: при динамическом индексе путь снова становится
  групповым. Нужно либо различать пути элементов, либо честно объявить
  ссылку на элемент ссылкой на группу.
- **Коллизии имён со стандартной библиотекой.** Имена пользовательских
  функций попадали в C без преобразования, и любая функция, названная как
  функция libc (`remove` из stdio.h, `index` из strings.h), приводила к
  конфликту типов. Исправлено префиксом `k_` в бэкенде, но правило должно
  быть зафиксировано в языке: любое имя пользователя может совпасть с
  имением из libc, и это не должно быть ошибкой.
- **Локальная переменная может перекрыть функцию libc.** Если назвать
  локальную переменную `printf` или `strcmp`, сгенерированный C не соберётся
  либо соберётся неверно. Сейчас локальные имена не преобразуются — это
  сделано ради читаемости вывода C, и решение надо пересмотреть, когда
  появится стандартная библиотека.
- **Сравнение строк.** Раньше `==` для строк сравнивал указатели, а не
  содержимое. Исправлено (`strcmp`), но в языке не определено, как
  вообще должны вести себя строки: это значения или указатели на
  неизменяемые данные? От ответа зависит, нужны ли строковые литералы
  во владении.
- **Ошибки без Option/Result.** Любая функция, которая может не найти
  запись или не найти место, вынуждена возвращать `-1`/`0` и печатать
  сообщение сама. Это не масштабируется: нужен либо `Option`, либо
  `Result`, либо идиома возврата ошибки.
- **Ссылка в поле структуры не может уехать из функции.** Раньше
  `return Holder(&i)` компилировалось без предупреждений, а чтение поля
  после возврата давало мусор (use-after-free). **Исправлено:** анализ
  выхода запрещает возвращать значение, содержащее ссылку на локальную
  переменную (п. 6 раздела 7.2).
- **C-backend наследует неопределённое поведение C.** Сейчас Keel
  транслируется в C, и всё, что C не определяет, не определяется и в Keel:
  порядок вычисления аргументов (`f(a(), b())` — какой раньше?), поведение
  при переполнении `int`, что происходит с неинициализированной памятью.
  Язык, обещающий безопасность памяти, не может оставлять такие вещи
  неопределёнными — пользователь должен знать, что получит. Это главная
  причина, по которой C-backend не годится для продакшена.
- **Диагностика на границе с C.** Ошибки времени компиляции, приходящие от
  `cc`, приходят словами gcc: «declaration of 'empty' as array of voids».
  Для пользователя Keel это нечитаемо. Нужен слой, переводящий ошибки C в
  диагностику Keel с указанием строки исходника. Дёшево, но чинит только
  симптом.

### 7.2. Порядок работы над долгами

1. **Калибровочный тест: `+=` и `if` как выражение.** Первое, что делаем
   дальше, — не долг, а измерение. Нужно понять, насколько реально
   занимает фича, прежде чем строить на оценках план. По оценке —
   день на каждую; если выйдет 2–3 часа, значит мои сроки завышены в
   3–5 раз на механической работе, и весь план раздела 8 пересчитывается
   соответственно.

   **Что именно делается:** составные операторы (`+=`, `-=`, `*=`, `/=`,
   `%=`) и `if` как выражение (`let m = if a > b { a } else { b };`).
   Обе — из волны 1 раздела 8, то есть часть нужной работы, а не
   отдельная трата.

   **Как измеряем:** замеряем обе раздельно и честно — включая время на
   осмысление, а не только на набор кода. Записываем результат в
   `docs/mvp-results.md` и пересчитываем сроки раздела 8.

   **Почему первым:** все сроки в разделе 8 — это мои оценки, а не
   измерения. Единственный способ узнать, завышены ли они, — проверить
   на одной фиче. Две фичи — минимум, который даёт пригодную цифру.

2. `Option`/`Result` и обработка ошибок — без этого прикладной код
   получается либо нечитаемым, либо полным `-1`.
3. Диагностика с цепочкой инвалидации (см. открытые вопросы в
   `keel-syntax.md`).
4. Запрет move из элемента массива.
5. Точность путей элементов коллекции.
6. **Ссылки в полях структур: время жизни.** Это не «было бы удобно»,
   а закрытие дыры в безопасности. Ниже — разбор с вариантами и
   оценкой.
   **Что происходит сегодня.** Проверено на компиляторе:

   - поле типа `&T` в структуре объявить **можно**;
   - конструктор ссылку **принимает** (`Outer(&i, 7)` — работает);
   - поле **читается** (`o.inner.x` — работает);
   - **но** ссылка может указывать на объект, который уже умер.

   Вот программа, которую компилятор принимает без единого
   предупреждения:

   ```keel
   struct Inner { x int; }
   struct Holder { r &Inner; }

   fn make() Holder {
       let i = Inner(42);
       return Holder(&i);      // ← ссылка на локальную переменную
   }

   fn main() int {
       let h = make();
       let junk = clobber();   // затирает стек
       print(h.r.x);            // ← 1 вместо 42
       return 0;
   }
   ```

   Это use-after-free: `i` жил на стеке `make`, а `h` читает его после
   возврата. Значение, как правило, ещё цело — но это случайность, а не
   гарантия.

   **Почему так.** Путь ссылки привязан к локальной переменной
   (`src/checker.rs`, `RefLocal { target: Path }`). Переменная умирает с
   кадром — а ссылка, уехавшая в структуре, переживает кадр. Никакой
   проверки «не уезжает ли ссылка за пределы функции» сейчас нет.

   **Варианты решения.**

   | | Что даёт | Цена | Оценка для Keel |
   |---|---|---|---|
   | **А. Запретить выезд** | Ссылки в полях вообще запрещены | Терять то, что уже работает | Мало: запретить структуры с `&`-полями и возврат таких структур. Но это откат возможности |
   | **Б. Поколения** (`Gen<T>`) | Ссылка = указатель + номер поколения; при обращении — сверка | Одна проверка на разыменование | Средне: нужен кучной аллокатор с нумерацией поколений (в Keel его нет вообще) и новый тип ссылки. Указатель станет 16 байт |
   | **В. Статические регионы** | Ноль рантайм-проверок, компилятор доказывает | Огромный анализ | Очень дорого: анализ регионов с вложенностью и изоляцией — работа масштаба LLVM |
   | **Г. Анализ выхода** (escape analysis) | Ссылка не может уехать из функции; поля со ссылками — только внутри | Ссылки в полях живут только локально | Мало-средне: найти все пути возврата значения, содержащего ссылку на локальную переменную, и запретить их |

   **Что выбрано: Г, реализовано.** Вариант Г закрывает дыру дёшево:
   правило «значение, содержащее ссылку на локальную переменную, не
   может быть возвращено из функции» проверяется в одном месте — при
   анализе возвращаемого значения. Ссылки в полях живут только внутри
   функции — это правило Rust: ссылка не живёт дольше области, где создана.

   **Как реализовано** (`src/checker.rs`). У каждой локальной переменной
   есть список `escapes` — ссылки на локальные, спрятанные внутри
   значения, вместе с путём до них (`[Field("r")]` для поля `r`).
   Список собирается рекурсивно при объявлении переменной: из ссылок,
   конструкторов структур, литералов массивов и ветвлений `if`.
   На `return` и на присваивании в поле ПАРАМЕТРА список проверяется:
   непустой — ошибка с указанием строки и пути.

   Различие «локальная или параметр» — по корню пути: у локальной это
   числовой uid, у параметра — имя. Вернуть ссылку на параметр можно
   (он живёт в кадре вызывающего), на локальную — нельзя.

   Проверено на компиляторе: 8 способов утечки (возврат ссылки, возврат
   структуры, массива, переменной со ссылкой внутри, поля, ссылки на
   поле локальной, запись в поле параметра) теперь дают ошибку, а 7
   законных случаев (ссылка на параметр, на элемент параметра-массива,
   ссылка на локальную внутри функции) по-прежнему компилируются.

   Вариант Б (поколения) — если понадобится, чтобы ссылка в поле жила
   дольше функции. Это уже требует кучи, а значит меняет модель памяти
   целиком: сейчас всё живёт на стеке, деструкторов нет, GC нет.

   Вариант В (статические регионы) отложен: он правильный по смыслу, но
   дороже остальных вместе взятых, а дыру закрывает и Б, и Г.

   **Побочный вывод.** Индексы (текущий обходной путь для графов) с
   регионами **не связаны**. Индекс отвечает на вопрос «какой элемент»,
   время жизни — на вопрос «дольше ли он живёт». Регионы нужны не
   чтобы перестать хранить индексы, а чтобы ссылка в поле была безопасна.

   **Следствие для языка.** Если выберем Г, то Keel — язык, где ссылки
   живут только внутри функции, а структуры со ссылками в полях —
   локальные. Это честное ограничение, и его надо написать в
   `keel-syntax.md`, а не прятать.

6. **Переход на собственный IR (Cranelift)** — когда фронтенд устоится.
   Оценка миграции и измеренные цифры — в `docs/cranelift-experiment.md`.
   Пункт стоит последним не потому, что он менее важен, а потому, что
   до него фронтенд всё равно меняется: переписывать кодогенерацию
   дважды невыгодно. Отдельно проверено, что SSA-конструктор писать
   не придётся: `cranelift_frontend::SSABuilder` строит SSA-форму сам,
   достаточно скормить ему AST Keel.
7. **Диагностика с кодами ошибок и подсказками.** Формат: код + причина
   (какое правило и где) + путь (что делать). Это закроет пункт 2
   частично и улучшит всё сразу: у Keel есть ошибки, которых нет ни у
   кого, — инвалидация ссылки, нарушение `mut`-контракта, move из
   элемента коллекции. Их нельзя объяснить одним словом «нельзя».
8. **Контракты `pre`/`post`.** Промежуточная ступень к `Option`/`Result`:
   проверка предусловий на границе функции с сообщением, вместо
   «`-1` значит ошибка». Позволяет начать решать пункт 1, не переписывая
   типы во всём коде.
9. **Синтаксис: `if` как выражение, `for` по диапазонам и коллекциям.**
   `if` как выражение убирает класс временных переменных. `for` по
   коллекции в Keel обязан обходить *элементы* — то есть он становится
   проверкой group borrowing, а не только удобством.
10. **`match` + `enum`.** В Keel нет ни того, ни другого. Исчерпывающий
    `match` по enum'у — путь к `Option`/`Result` (пункт 1), причём
    дешевле, чем сами типы-обёртки.
11. **Собственный минимальный рантайм.** Нужен для своего аллокатора →
    поколений (`Gen<T>`) → варианта Б в пункте 5; для собственной
    семантики вместо C; для меньшего бинарника.

### 7.3. Про C-backend и миграцию на Cranelift

Коротко, чтобы не искать по документу.

**Что мы имеем сейчас.** Keel → текст C → `cc` → машинный код. Текст C
генерирует мой кодогенератор, машинный код — gcc. Диагностика частично
моя (checker), частично gcc.

**Что даст Cranelift.** Свой IR, свой машинный код, своя диагностика,
своя семантика — вместо унаследованной от C. Цена — в ~4.5 раза больше
кода в кодогенераторе и необходимость строить SSA-форму самому.

**Почему не сейчас.** Эксперимент показал: полный цикл компиляции сейчас
занимает ~30 мс, из которых кодогенерация — около 30 мс, а фронтенд —
доли миллисекунды. Cranelift кодогенерирует за ~2 мс. То есть выигрыш в
скорости — десятки миллисекунд, а не порядок величины. Главный выигрыш
(своя семантика вместо неопределённого поведения C) нужен перед
продакшеном, а не во время проверки идеи.

**Что делаем вместо.** Пока фронтенд не устоялся — держим C-backend и
чиним его границы: переводим ошибки gcc в диагностику Keel. Это дёшево
и снимает самый неприятный симптом.

**Ещё одно соображение: качество кода важнее скорости сборки.**
Cranelift выигрывает у LLVM **не по качеству сгенерированного кода, а по
скорости компиляции** — это разные вещи, и их регулярно путают.
`rustc_codegen_cranelift` формулировался как «компилировать Rust быстрее,
ценой небольшого ухудшения качества кода»: нет ThinLTO, ограничен PGO,
не все LLVM-фичи поддержаны.

Для Keel это решающий довод: текущий бэкенд отдаёт код **зрелому
оптимизатору** (`cc` с `-O2`) бесплатно. Переход на Cranelift был бы
разменом «быстрее компиляция → медленнее готовый код», а для системного
языка это плохой размен. **Значит, миграция оправдана не сама по себе, а
только при появлении конкретной потребности:**

- WASM-бэкенд (нужен собственный таргет, а C — не таргет);
- собственный рантайм (тогда C-backend всё равно придётся обходить);
- самокомпиляция Keel (тогда скорость сборки становится значимой).

До появления одной из этих причин — C-backend.

Полный эксперимент с кодом и замерами: `docs/cranelift-experiment.md`.
Сравнение Cranelift и LLVM подробнее: `docs/links.md`, раздел 3.

### 7.4. Что берём из Zeta

Zeta — единственный язык с той же целью, что и Keel: безопасная память,
простой синтаксис, быстрая компиляция. Разбор по репозиторию — в
`docs/zeta-comparison.md`. Здесь только выводы, влияющие на дизайн.

**Проверено и важно.** Ветка `main` — чистый Zeta (52 файла `.z`, ни одного
`.rs`), Rust-реализация намеренно живёт на ветке `bootstrap`. Semiring-
свёртки, инварианты циклов, `comptime` и концепты в Rust-версии
реализованы. А вот `#[commutative]`/`#[associative]`, решётка
`Regular→…→Ring` и CacheSafe TBAA — **не реализованы**: атрибуты
парсятся, но на оптимизацию не влияют; `noalias` в кодогенераторе — ноль.

**Что берём** (пункты 7–11 раздела 7.2): коды ошибок с подсказками,
контракты `pre`/`post`, `if` как выражение, `for`, `match` + `enum`,
собственный минимальный рантайм.

**Чего не берём:**

- **Атрибуты-законы для пользовательских операций.** Это утверждение
  программиста, которое никто не проверяет. Ошиблись — компилятор
  перегруппирует вычисления и получит неправильный результат: тихий баг
  оптимизации, худший его вид.
- **Решётку уточнения концептов** — это работа масштаба системы
  доказательств.
- **Borrow-модель Zeta.** Там Rust-правило «один писатель или много
  читателей», то есть ограничения Rust'а по построению.

**Где Keel может быть лучше.** Zeta предлагает пользователю объявлять
законы, которые компилятор и так знает: ассоциативность целочисленного
сложения выводится из того, что сложение — примитив. То же с алиасингом:
у Keel есть **точная** информация о непересечении по путям, а у Zeta —
грубая «один писатель или много читателей».

Отсюда самое дешёвое, что можно сделать прямо сейчас:

```
int64_t k_sum_sq(int64_t *restrict a) { ... }
```

Компилятор знает, что `&world.entities[0]` и `&world.entities[1]` не
пересекаются, — значит, может честно сказать gcc, что память не
пересекается, и тот оптимизирует цикл свободнее. Информация уже на
руках; стоит одна строка в кодогенераторе.

**О синтаксисе.** Zeta пишет `x: int`, Keel — `x int` (как в Go).
Решение — **оставить `x int`**, и вот почему: Keel уже в согласии с Go;
его отличие от других языков — модель владения, а не синтаксис; и
добавление двоеточия дало бы три разные формы записи типов (объявление,
параметр, параметр-внутри) вместо одной. Полный разбор — в
`docs/zeta-comparison.md`, раздел 5.

### 8.3. Почему порядок именно такой

**Куча в этом объёме не нужна — и это меняет дело с замыканиями.** В Keel
значения копируются, а структуры возвращаются по значению. Значит,
замыкание можно представить как **структуру: захваченные значения +
указатель на функцию**. Если захват помещается в структуру, замыкание
живёт на стеке, без аллокатора — идеально для философии «стек по
умолчанию».

Это отличает Keel от подходов, где любое замыкание требует кучи. Оговорка:
если захватывается что-то крупное или по ссылке, понадобится либо
смещение в куче, либо ограничение «захват только по значению». Первое
выводит на волну аллокатора (пункт 11 раздела 7.2), второе — ограничение
языка, и его надо выбрать осознанно.

**`for` по массиву — проверка модели, а не только удобство.** Итерация
должна отдавать *элемент*, а не ссылку на контейнер: иначе изменить
элемент во время обхода нельзя, и смысл group borrowing теряется. Это
первая возможность проверить модель на коде, который никто специально под
нее не писал.

**`enum` без `match` — почти бесполезен.** Вариант можно различить только
по тегу, без разбора содержимого. Поэтому в волну 4 включён минимальный
разбор по тегу: это немного, но без него `enum` не даёт ничего. Полный
`match` с деструктуризацией остаётся вне объёма — и это отдельная задача,
для которой понадобится продумать, как паттерны взаимодействуют с
правилом стабильности формы (переключение варианта = мутация формы =
инвалидация ссылок внутрь).

**SIMD.** Автовекторизация приходит из бэкенда: Keel генерирует C, и gcc
векторизует циклы по массивам фиксированного размера сам — это уже
проверено.

**Про `restrict` — обещание не подтвердилось, замер сделан.** В плане
стояло «передать gcc информацию о непересечении через `restrict` из
путей, одна строка, выигрыш сразу». Проверено на компиляторе и
замерено:

1. **Выигрыша нет.** gcc 15 и clang сами версионируют циклы (runtime
   alias check): генерируют быструю векторизованную версию и медленную
   на случай пересечения. Замер на 300 000 повторов, массив в кэше:
   `-O2` разница в пределах шума (±3%), `-O3` — 0.200 с против 0.200 с.
   Проверены три сценария (длинный цикл, короткий цикл из 8 элементов,
   вызов функции внутри цикла) — везде ноль.
2. **Риск реальный, а не теоретический.** Keel **разрешает** передать
   один массив дважды: `f(&a, &a)` проходит проверку. При этом
   `restrict` — обещание, что память не пересекается. Проверено: тело
   `x[i] = x[i] + y[0]`, вызванное как `f(a, a)`, без `restrict` даёт
   `[2, 3, 3, 3, 3]`, с `restrict` — `[2, 2, 2, 2, 2]`. Молча неверный
   результат, не падение.

Отсюда решение: **`restrict` из путей не ставим.** Информация о путях
неполна — она про пути *внутри* функции, а алиасинг возникает на
вызове, где компилятор путей не видит. Ставить `restrict` можно было бы
только с межпроцедурным анализом алиасинга, а это уже не «одна строка».

Место `restrict` остаётся в интеропе с C: горячий участок выносится в
написанный руками C, где автор сам отвечает за непересечение
(см. п. 6 в `docs/keel-risks.md`). Это и было записано в рисках.

### 8.4. Где Keel будет отличаться

**Модель владения.** В туре Zeta сказано: «No lifetimes, no borrow checker
complexity. Ownership is tracked simply: one writer or many readers». Это
правило Rust'а — оно запрещает две изменяемые ссылки на разные элементы
одной коллекции.

У Keel правило другое: **право писать определяется владельцем пути**, и
две изменяемые ссылки на *разные* элементы разрешены. Значит, обход
коллекции в Keel сможет отдавать элементы, которые можно менять
независимо, — и `for v in array` станет рабочей проверкой модели, а не
формальностью.

#### 8.4.1. Что показала проверка Zeta эмпирически

**Не «хуже, чем в Rust», а «гарантии нет вообще».** Проверено на
компиляторе `zetac` v1.0.21 и по исходникам (`src/frontend/borrow.z`,
169 строк; ветка `bootstrap` — `src/frontend/borrow.rs`).

| Свойство | Zeta |
|---|---|
| Проверка статическая | Да, `BorrowChecker::check` вызывается из `typecheck` |
| Ошибка останавливает компиляцию | Да — `typecheck` возвращает `false` |
| Ловит use-after-move | Да, `E7002` «Use of moved value» |
| Ловит конфликт двух `&mut` | **Нет** — состояние просто перезаписывается |
| Ловит неизвестную переменную | Да, `E3003` |
| Гранулярность | **По имени переменной**, не по пути |
| `let` обрабатывается | **Нет** — `AstNode::Let` в `check()` не встречается |

Ключевое: `BorrowState` — это `Owned | Borrowed | MutBorrowed | Consumed`,
но переходы **не проверяют предыдущее состояние**. Строка
`self.borrows.insert(name.clone(), BorrowState::MutBorrowed);` просто
затирает прежнее значение. Проверки «уже `MutBorrowed` → ошибка» в коде
нет. `SpeculativeState` — заглушка, в комментарии `always Safe`.

**Ссылок в языке нет вообще.** В 37 вариантах `AstNode` нет ни одного для
ссылки или разыменования. `&` и `&mut` не являются синтаксисом ссылок:
парсер трактует `&` как побитовое И, а `&mut` компилируется в **вызов
функции с именем `&mut`** — линкер падает с
`undefined reference to '&mut'`.

**«No lifetimes» — следствие отсутствия ссылок, а не достижение.**
Ссылку нельзя создать, сохранить, передать — значит, нет aliasing'а, и
lifetime'ы не нужны. Простота получается за счёт того, что язык не даёт
инструмента.

**Как Zeta обходится без ссылок: структура — это handle на куче.**

```
%struct_heap = call i64 @runtime_malloc(i64 8)
%struct_base = inttoptr i64 %struct_heap to ptr
%field_ptr = getelementptr i64, ptr %struct_base, i64 0
store i64 10, ptr %field_ptr
store i64 %struct_heap, ptr %2        ; в переменную кладётся указатель
```

То есть переменная типа «структура» — это `i64`, внутри которого адрес
кучи. Компилятор считает, что структура скопирована (move-only по
имени), а в рантайме это **указатель**. Отсюда:

- `let s2 = s;` — один `malloc`, ноль `free`: копируется handle, буфер
  разделяется. Move не реален, копия фиктивна.
- **Запись в поле структуры не работает.** `s.hp = 7;` компилируется в
  `store i64 7, ptr %6` — запись во *временную переменную*, а не в
  поле. Программа печатает `1` вместо `7`. Это подтверждено IR'ом.
- `runtime_free` **не вызывается нигде** — в сгенерированном коде нет ни
  одного вызова освобождения. Память течёт.

**Итог по владению: у Keel проверка строго сильнее, чем у Zeta.** Keel
различает `a[0]` и `a[1]` (путь), ловит конфликт на одном пути, запрещает
use-after-move. Zeta различает только имена переменных, конфликты не
ловит вовсе, а структуры в рантайме — это указатели, которые компилятор
считает значениями.

**Из Zeta стоит брать синтаксис, а не владение.** Именно на этом
различии и построен план раздела 8: волны 1–5 — это языковые
возможности, которых у Keel нет, и которые в Zeta хотя бы
предположительно работают; владение в Keel уже сделано и сделано лучше.

**И не заявления, а код.** Zeta написан с участием ИИ-агента: в
`docs/bootstrap/` лежат 248 отчётов каждые полчаса, в ROADMAP — «Autonomy
system with heartbeat monitoring deployed». Отсюда годовой темп, не
совместимый с одним человеком, и маркетинг тура, опережающий код:
запись в поле структуры не работает, `runtime_free` не вызывается,
`&mut` — вызов функции. **Каждое обещание тура проверяется компилятором;
иначе оно окажется неправдой** (подробности — `docs/zeta-comparison.md`,
раздел 6).

**Замыкания без кучи.** Как описано в 8.3: замыкание — структура, а не
указатель на аллокатор. Это дешевле и лучше согласуется с «стек по
умолчанию». В Zeta это невозможно по построению: любое значение там —
это `i64`, а структура — handle на куче.

**Синтаксис.** Остаётся `x int`, а не `x: int` — обоснование в
`docs/keel-syntax.md` и `docs/zeta-comparison.md`, раздел 5. Заметим,
что Zeta использует `a: i64` в параметрах и `struct S { hp: i64 }` с
двоеточием; это несовместимо с Keel, поэтому двоеточие не берём.

**Имена.** `str` против `string`, `println_str` против `print` — мелочи,
но при выборе стоит держать `string` (уже привычнее в Keel) и не плодить
`println_*`: один `print` с перегрузкой по типу аргумента понятнее, чем
десяток функций. У Zeta рантайм объявляет сразу тридцать функций
(`print_i64`, `print_bool`, `print_str`, `println_str`, `array_*`,
`map_*`, `option_*`, `channel_*`) — это следствие того, что типов мало и
нет перегрузок.


### 8.5. Разбор: чего не хватает настоящей программе

Волны 1–6 пришли из ту́ра Zeta — то есть из списка выразительных
возможностей языка. Но реальной программе нужны ещё вещи, которых в ту́ре
нет вовсе. Чтобы список не был выдуман, он составлен разбором настоящего
файла: `play/main.keel` (реестр пользователей: структуры, методы,
массивы, циклы, модули). Каждый пункт проверен компилятором — вот что
именно не работает:

| Что пробуем | Что отвечает компилятор |
|---|---|
| `len(users)` | `неизвестная функция len` |
| `const MAX = 100;` | `ожидалось 'struct', 'fn', 'impl' или 'import', получено 'const'` |
| `println("a", x)` | печатает только один аргумент |
| `a + " world"` | `арифметика требует int, получено string и string` |
| `read_line()` | `неизвестная функция read_line` |
| `argc()` | `неизвестная функция argc` |
| `enum Color { ... }` | `ожидалось 'struct', 'fn', 'impl' или 'import', получено 'enum'` |
| `let x f64 = 3.14;` | `ожидалось имя, получено число 14` |
| `5 > 3 ? 1 : 0` | `неожиданный символ '?'` |
| `5 & 3` | `ожидалось ';', получено '&'` |
| `let t = (1, "two");` | `ожидалось ')', получено ','` |
| `let v Vec<int> = ...` | `обобщённые типы не поддерживаются в MVP` |

**Самое показательное — `len`.** В `play/main.keel` есть строка:

```
let count int = 3;
let registry Registry = Registry(users, count);
```

Число `3` вписано руками. Если в массиве станет четыре элемента,
`count` останется тремя, и `for i in 0..count` **молча** пропустит
последний. Компилятор этого не поймает: `count` — обычная переменная.
Это ровно тот класс ошибок, который Keel в другом месте ловит (устаревшая
ссылка, перемещённое значение), но здесь ловить нечем — нет способа
узнать размер массива.

**Порядок внутри волны 7 — по возрастанию сложности, а не по важности.**
Первые шесть пунктов (5 часов) дают язык, на котором пишут консольные
программы. Последние два (`file` в диагностике, `pub`) — про удобство
работы с несколькими файлами, что стало актуально после модулей.

**Что в волне 7 намеренно не берётся.** `Vec` и куча (волна 8) — потому
что это меняет модель владения, а не добавляет функцию. `Option`/`Result`
— зависят от `enum`. Работа с файлами — нужны строки переменной длины,
то есть куча.

### 8.6. Что это даёт кроме списка фич

Ни одна из этих волн не трогает модель владения — они всё делают *поверх*
неё. Это и хорошо (значит, работа не рискует главным), и плохо (значит,
ни одна из них не приближает к цели, ради которой Keel затевался).

Главное, что даёт именно эта работа: **язык, которым можно написать
что-то**. Сейчас Keel умеет показать свою модель на четырёх примерах, но
написать на нём настоящую программу — нельзя: нет `f64`, нет кортежей, нет
замыканий, нет `enum`/`match`, нет методов, нет стандартной библиотеки.
Пока нет стандартной библиотеки, любые оценки «Keel пригоден для
веб-сервера» остаются умозрительными.

Отсюда и порядок: **сначала довести язык до состояния, в котором на нём
можно писать, потом — оптимизировать и проверять модель на реальном
коде.** Пункт 6 раздела 7.2 (анализ выхода) стоит перед этими волнами
именно поэтому: дыра в безопасности недопустима даже в языке, который
пока нельзя использовать.

**Чего в этом объёме нет и почему это сознательно.** За пределами
объёма остаются `match` с деструктуризацией, дженерики с концептами,
`Vec` с кучей и CTFE. Первые три — крупные задачи, каждая тянет за собой
изменения в модели проверки или в памяти. Их стоит делать, когда базовый
язык устоялся: иначе придётся переписывать кодогенерацию и проверку
второй раз. CTFE — отдельная история: он требует интерпретатора AST, а
значит, стабильности грамматики; делать его до того, как грамматика
устаканилась, — значит переделывать.
