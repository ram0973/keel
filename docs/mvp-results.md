# Keel — результаты MVP и размышления по ходу

Дата: ноябрь 2026. Проект: `/home/ra/keel`.

Документ отвечает на два вопроса: что MVP доказал и что он сломал. Второй
важнее: дизайн до реализации и дизайн после — разные вещи.

---

## 1. Что построено

Компилятор на Rust, бэкенд — генерация C.

| Файл | Строк | Назначение |
|---|---|---|
| `src/lexer.rs` | 137 | Токены: идентификаторы, числа, строки, операторы |
| `src/ast.rs` | 261 | AST, типы, пути (`Path`, `Seg`) |
| `src/parser.rs` | 557 | Рекурсивный спуск, приоритеты выражений |
| `src/checker.rs` | 912 | **Ядро**: владение, move, пути, инвалидация, контракты |
| `src/codegen.rs` | 378 | Генерация C (составные литералы, прототипы, указатели) |
| `src/lib.rs` + `src/main.rs` | 136 | API и CLI (`check` / `build` / `run`) |
| `tests/checker.rs` | 380 | 20 тестов семантики |

Итого 2761 строка, из них 912 — проверщик.

**Реализованное подмножество языка:** `int`, `bool`, `string`, структуры с
полями, массивы `[T; N]`, функции с тремя видами параметров (владение,
`&T`, `x in path`), `let` / присваивание / `return` / `if` / `while`,
арифметика и сравнения, `&expr`, встроенная `print`.

**Не реализовано:** обобщённые типы, `Vec`, `Option`/`Result`, лямбды,
трейты, `enum`, модули, асинхронность, Higher RAII, generational
references, ссылки в полях структур.

**Метрики:**

| Проверка + генерация C программы | 0.01 с |

| Тестов | 20, все проходят |

## 2. Главное доказательство

Один и тот же код на двух языках.

**Rust** (`examples/rust/rust_comparison.rs`) — не компилируется:

```
error[E0499]: cannot borrow `world.entities` as mutable more than once at a time
error[E0502]: cannot borrow `world.entities` as mutable because it is also borrowed as immutable
```

**Keel** (`examples/tour.keel`) — компилируется и работает:

```
fn step(world &World, entity in world.entities[] mut, amount int) {
    entity.hp = entity.hp - amount;
}

fn heal_first_and_second(world &World) mut(world.entities[]) {
    let a = &world.entities[0];
    let b = &world.entities[1];
    a.hp = a.hp + 10;
    b.hp = b.hp + 10;
}
```

Вывод программы:

```
--- начальное состояние ---
100
80
50
--- после step(-30) ---
70
--- после лечения первых двух ---
80
90
--- имена ---
orc
rat
```

То есть **ключевое обещание модели подтверждено**: то, что Rust запрещает
как «слишком строгое правило», в Keel — обычный код, и при этом
use-after-free по-прежнему ловится на этапе компиляции (тесты это
проверяют).

Второе обещание — **отсутствие ложных срабатываний** — тоже держится:
замена объекта убивает ссылки внутрь него, но не ссылку на сам объект
(тест `ссылка_на_весь_объект_не_инвалидируется_при_изменении_поля`).

## 3. Что пришлось изменить в дизайне

### 3.1. «Право писать» и «область инвалидации» — это разные вещи

Самое важное открытие. В исходном дизайне `mut` в сигнатуре был описан
одной фразой: «функция изменяет эти пути». При реализации выяснилось,
что этой фразой покрываются две независимые проверки, и смешивать их
нельзя.

**Право писать**: «можно ли выполнить эту запись?» Ответ определяет
владелец пути — локальная переменная (`let mut`) либо параметр
(mut-контракт).

**Область инвалидации**: «что у вызывающего станет недействительным после
вызова?» Это и есть контракт.

Когда проверки были объединены, получилось две разные поломки:

- Если проверять «путь записи должен быть объявлен» для всего — ломается
  обычная локальная запись (`let mut x = 1; x = 2;` не объявляет `x`),
  то есть язык становится непригодным.
- Если проверять только по владельцу — теряется инвалидация у вызывающего:
  контракт перестаёт что-либо значить.

В MVP они разведены: `ctx.declared` отвечает за контракт, владелец пути —
за право записи. Это ровно то различие, из-за которого в Rust две
независимые системы (`&`/`&mut` в типах и lifetimes в аннотациях).

**Практический вывод:** если бы мы проектировали язык заново, стоило бы
сразу развести эти понятия в синтаксисе — например, разные слова для
«я могу писать сюда» и «я меняю это». Сейчас оба выражаются через `mut`,
и это источник путаницы.

### 3.2. Сегмент `[]` — шаблон, а не конкретный индекс

Изначально пути сравнивались буквально: `world.entities[]` не считался
префиксом `world.entities[0].hp`. Из-за этого объявить контракт на уровне
коллекции было невозможно — пришлось бы перечислять элементы.

Семантика Valen здесь элегантнее: `[]` обозначает *группу* элементов и
совпадает с любым конкретным индексом. После этого `mut(world.entities[])`
работает как контракт на коллекцию.

### 3.3. Два вида инвалидации

Пришлось различать:

- **Replace** — значение по пути заменено целиком (`x.f = v`). Убивает
  ссылки на сам путь и всё внутри него.
- **MutateInside** — содержимое изменено, объект остался на месте
  (`vec.push(..)`). Убивает только ссылки строго внутри.

Смешение этих двух давало либо слишком строгую проверку (убивало ссылку на
сам контейнер при `push`), либо пропускало реальный use-after-free.

### 3.4. Пути параметров — символические

Путь параметра — это имя параметра, а не локальный идентификатор. Именно
это позволяет переносить контракт вызываемой функции в пространство
вызывающего: `mut(world.entities[])` внутри функции превращается в путь
вызывающего при вызове. Если бы пути параметров были локальными,
межпроцедурная проверка не работала бы вовсе — а именно она даёт
келограмму.

### 3.5. Проверщик обязан быть детерминированным

Обнаружено случайно: тесты прошли на Windows, упали в WSL. Причина —
владелец пути искался обходом `HashMap`, и при равных кандидатах
выбирался произвольный. Результат зависел от seed'а `RandomState`.

Это худший вид ошибок в компиляторе: «иногда компилируется, иногда нет».
Нашлось только потому, что тесты гонялись в двух окружениях — при
одном окружении такой баг мог бы прожить долго.

Исправление: у локальной переменной появился явный `uid`, поиск идёт по
нему, ничьи решаются по `uid`. Общее правило, которое стоит записать в
код-стайл: **любой выбор «один из нескольких равноправных» должен
разбиваться по стабильному идентификатору, а не по порядку обхода**.

## 4. Ошибки, найденные при реализации

Список полезен как чек-лист для следующих версий.

| Ошибка | Симптом | Причина |
|---|---|---|
| Локальные ссылки не регистрировались | Инвалидация не срабатывала ни на одном тесте | В `let` тип ссылки не отличался от типа значения |
| Mut-контракт требовался для локальных переменных | `let mut x = 1; x = 2;` не компилировалось | Пути локалей и пути параметров не различались при проверке контракта |
| Парсер не понимал `mut(e)` | `expected '{', got '('` | `mut` конфликтовал с разбором типа возврата |
| Тип параметра-внутри не выводился | `void — не структура` | Тип элемента выводился, но не передавался в кодогенератор |
| Кодогенератор не умел конструкторы структур | Невалидный C | Конструктор эмитился как вызов функции |
| Нет прототипов функций | `implicit declaration of function` | C требует объявления до вызова |
| Недетерминированность проверщика | Тесты падали в WSL | Обход `HashMap` |
| Массивы не инициализировались | Невалидный C | C не допускает присваивания массиву |
| Ссылки на элемент теряли владельца | Ложные ошибки записи | Владелец искался по корню пути, а не по префиксу |

Последние два — не ошибки модели, а ошибки реализации, и они показали,
что модель требует аккуратной работы с путями: путь ссылки на элемент
(`arr[0].hp`) и путь её владельца (`arr`) — это разные вещи, которые
легко спутать.

---

## 5. Что подтвердилось из списка рисков

- **Грубая инвалидация (п. 4) — реален и заметен.** Переход от точного
  контракта `mut(world.entities[0])` к грубому `mut(world.entities[])`
  ломает инвалидацию у вызывающего. Это та самая цена точности, о которой
  шла речь: чем грубее контракт, тем больше ложных запретов у вызывающих.
- **Диагностика (п. 8) — подтвердилась сразу.** Сообщения перечисляют
  пути, но не показывают цепочку инвалидации («здесь объявлено → здесь
  изменено → здесь использовано»). Для языка, чьё обещание — «проще
  Rust», это сейчас главный дефект.
- **Нет GC — не значит нет накладных расходов, но и накладных расходов
  проверки не видно.** Проверка выполняется один раз за функцию, в
  рантайме лишних проверок нет вообще. Но это масштаб MVP, а не язык
  целиком: при появлении generational references появятся и рантайм-проверки.

## Что не подтвердилось

- **«Ослабляем ограничения — значит, придётся доказывать больше» — на
  практике не проявилось.** Правило «инвалидировать ссылки внутри пути»
  оказалось простым: проверка каждой ссылки — это сравнение путей.
  Плата предсказуемость оказалась не в сложности анализа, а в точности
  контракта и в диагностике. Это хорошая новость: главный системный риск
  проекта, который я считал определяющим, на практике пока не
  подтвердился.

Но оговорка: MVP не проверяет то, что проверка идёт по группам элементов с
неконкретными индексами, не проверяет циклы с произвольной структурой и не
проверяет взаимодействие с `Gen<T>`. Там сложность ещё впереди.

## 6. Что не работает и почему

**Ссылки в полях структур.** Главное ограничение v0, и оно не является
ошибкой — это сознательный размен: внутрипроцедурная проверка вместо
межпроцедурной. Цена: любая долгоживущая структура (граф, дерево, кэш с
обратными ссылками) пишется через индексы, а не через ссылки. То есть
часть «простоты C» выменивается обратно на «возню с индексами», которую мы
ругали в Rust.

**Точность контракта.** `mut(world.entities[])` — контракт на уровне
коллекции; `mut(world.entities[0])` — точнее, но при переходе к грубому
ломает инвалидацию. Что будет умолчанием — не решено.

**Диагностика.** Пока перечисляет пути, а не показывает цепочку
инвалидации. Это отдельная работа и отдельная ценность: без неё «простой
синтаксис» обернётся непостижимыми сообщениями.

**Циклы.** Тело цикла проверяется двумя проходами: второй проход стартует
с состояния после первого и ловит использование ссылки, инвалидированной
в предыдущей итерации. Грубо, но работает. Точное решение — обратный
обход, как в Valen.

**Нет формальной верификации.** Rust имеет доказательство корректности
модели заимствования. У Keel нет ничего, кроме тестов. Риск пропустить
реальный use-after-free реален и не снижен тем, что MVP работает.

## 7. Что дальше, по приоритету

1. **Диагностика с цепочкой инвалидации.** Без неё язык непригоден для
   реальных пользователей, даже если модель верна. Показывать: где
   объявлено, где изменено, где использовано.
2. **`Vec<T>` и обобщённые типы.** Без коллекций нельзя написать
   веб-сервер, а без обобщённых типов — описать общую логику для
   коллекций. Это блокер для практической пользы.
3. **`Option`/`Result` и обработка ошибок.** Без них любой вызов,
   возвращающий значение, требует либо sentinel, либо паники.
4. **Регионы для ссылок в полях структур.** Снимает ограничение v0 —
   самый дорогой пункт, но именно он превращает язык из «учебного» в
   «пригодный для графа данных».
5. **Обратный обход вместо двух проходов по циклу.** Точность.
6. **Формальная или хотя бы исчерпывающая тестовая проверка.** Проверка
   того, что checker никогда не пропускает use-after-free, — через
   исчерпывающие тесты на малом подмножестве или через модель.

Пункты 1–3 — то, что превращает MVP в язык, на котором можно написать
что-то настоящее. Пункт 4 — то, что превращает его в язык общего
назначения.

## 9. Что вскрыли прикладные примеры

Тесты семантики проверяют модель в изоляции. Настоящий код, похожий на
прикладной, вскрыл другое — и в основном другое.

**Авторазыменование отсутствовало.** Сортировка пузырьком, где две ссылки
на соседние элементы используются для сравнения, потребовала `x > y` для
ссылок. Реализовано: если тип выражения — ссылка, в значенческих контекстах
(арифметика, сравнения) оно разыменовывается. Это соответствовало дизайну
с самого начала («нет `->`, авторазыменование»), просто не было сделано.

**Строки сравнивались по адресу.** `a == b` для строк эмитился в C как
сравнение указателей — то есть работал случайно, а для содержимого двух
одинаковых строк мог дать ложь. Поиск по имени в телефонной книге это
обнаружил бы сразу. Исправлено: `strcmp`.

**Имена столкнулись со стандартной библиотекой.** Функция `remove` из
примера не совпала с `remove` из `stdio.h` — C отказался собираться. Это
пробел языка, а не примера: любое имя пользователя может совпасть с
именем из libc. Исправлено префиксом `k_` для пользовательских функций.
Локальные переменные по-прежнему не преобразуются — это сделано ради
читаемости C-вывода, и решение пересмотреть при появлении стандартной
библиотеки.

**Ошибки без Option/Result.** Любая функция, которая может не найти
запись, вынуждена возвращать `-1` и печатать сообщение сама. Для учебного
примера терпимо, для настоящей программы — нет.

**Move из элемента массива не ловится.** `book.entries[j] =
book.entries[j + 1]` в Rust запрещено: элемент остался бы дырой. Наш
checker помечает перемещённым только простые переменные. В рантайме это
сейчас безопасно (значение копируется, деструкторов нет), но дыра
семантическая.

**Групповая гранулярность путей.** Ссылка на элемент коллекции указывает
на группу `book.entries[]`, а не на конкретный индекс. После сдвига
записей (удаление) ссылка формально жива, хотя указывает на другую запись.
Это самая заметная шероховатость модели: она проявляется именно на
прикладном коде с коллекциями, который меняет их содержимое.

Полный список — в `docs/lang-design.md`, раздел 7.1.

## 10. Общий вывод

MVP выполнил свою задачу: **модель group borrowing реализуема и даёт то,
что обещала**. Проверка заимствований на путях оказалась проще, чем
ожидалось, — около 900 строк на лексер, парсер, типы и всю семантику
владения. Это самый важный результат: главный риск проекта (что
ослабление правил Rust потребует более тяжёлого анализа) не
подтвердился.

Одновременно MVP показал, что **цена переносится в другое место**, чем мы
ожидали. Мы думали, что заплатим сложностью анализа; на практике платим
точностью контракта и качеством диагностики. Это другой и, что важно,
более решаемый вид долга.

Нерешённым остаётся главное: **проверка опирается на наше понимание
семантики, а не на доказательство**. Тесты показывают, что модель ведёт
себя как задумано, но не показывают, что задуманное — правильно. До
появления либо формальной верификации, либо исчерпывающих тестов этот
язык нельзя называть безопасным — можно называть «безопасным по нашему
пониманию».
