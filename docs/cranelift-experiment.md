# Эксперимент: бэкенд на Cranelift вместо C

**Цель.** Не «сделать компилятор», а измерить: сколько реально стоит
заменить генерацию C на генерацию настоящего IR, и что это даёт.

**Дата.** Ноябрь 2026. Cranelift 0.137.1.

**Итог одной строкой.** Работает, но дороже, чем я думал, и даёт меньше,
чем ожидал, — по скорости. Главный выигрыш в другом: своя семантика
вместо унаследованной от C.

---

## 1. Что сравнивали

Одна и та же функция из компилятора Keel:

```keel
fn sum_sq(a [int; 4]) int {
    let mut total = 0;
    let mut i = 0;
    while i < 4 {
        total = total + a[i] * a[i];
        i = i + 1;
    }
    return total;
}
```

Текущий путь: Keel → текст C → `cc` → машинный код.

```c
static int64_t k_sum_sq(int64_t a[4]) {
  int64_t total = INT64_C(0);
  int64_t i = INT64_C(0);
  while ((i < INT64_C(4))) {
    total = (total + (a[i] * a[i]));
    i = (i + INT64_C(1));
  }
  return total;
}
```

Альтернатива: та же логика, построенная напрямую в CLIF (Cranelift IR).
Код — `experiments/clif/src/main.rs`.

---

## 2. Что получилось

Классический цикл превращается в три базовых блока с параметрами:

```
function u0:0(i64) -> i64 system_v {
block0(v0: i64):
    v1 = iconst.i64 0
    v2 = iconst.i64 0
    jump block1(v1, v2)

block1(v3: i64, v4: i64):
    v8 = iconst.i64 4
    v9 = icmp ult v4, v8
    brif v9, block2(v3, v4), block3(v3)

block2(v5: i64, v6: i64):
    v10 = iconst.i64 8
    v11 = imul v6, v10
    v12 = iadd.i64 v0, v11
    v13 = load.i64 notrap aligned v12
    v14 = imul v13, v13
    v15 = iadd v5, v14
    v16 = iconst.i64 1
    v17 = iadd v6, v16
    jump block1(v15, v17)

block3(v7: i64):
    return v7
}
```

Обратите внимание на блоки 1 и 2: `total` и `i` — это **параметры блока**,
а не переменные. Это замена `phi`-инструкций: значение, определённое в
нескольких местах, «встречается» в точке соединения веток.

### Проверка результата

Три независимых способа:

| Способ | Результат |
|---|---|
| JIT-вызов `main()` | `main() вернул: 30` |
| AOT: объектный файл + линковка с C | `sum_sq = 30` |
| Дизассемблирование | цикл и вызов на месте, `cmp $0x4,%r8; jb` |

Ожидаемое значение — 30 (1+4+9+16). Совпало.

## 3. Объём работы

| | C-бэкенд | Cranelift-бэкенд |
|---|---|---|
| Код для этой функции | ~12 строк C-текста | ~55 строк Rust |
| Что нужно знать | синтаксис C | SSA, базовые блоки, параметры блоков, типы значений, стековые слоты, ABI вызова |

**~4.5× по объёму.** Моя прежняя оценка «3–5×» попала в точку.

Но качественная разница важнее количественной:

- **C-бэкенд**: «напечатать текст, который gcc превратит в SSA». Всю
  тяжёлую работу делает gcc.
- **Cranelift-бэкенд**: **я сам строю SSA-форму**. Это и есть настоящая
  работа. `jump` и `brif` требуют явных аргументов блоков, `load` —
  явных `MemFlags`, стековые слоты описываются структурой `StackSlotData`.

### Подводные камни API (0.137)

Набил шишки — список на будущее:
- `Module` — это **трейт**, а не структура. Конкретный модуль выбирается
  отдельно: `JITModule` или `ObjectModule`.
- `emit()` живёт на `ObjectProduct`, а не на `ObjectModule`. Путь:
  `ObjectModule::finish() -> ObjectProduct`, затем `.emit()`.
- `MemFlags::trusted()` на самом деле `MemFlagsData::trusted()`.
- `brif` принимает аргументы в порядке
  `(c, then_label, then_args, else_label, else_args)`.
- `jump`/`brif` принимают `&BlockArg`, а не `&Value`:
  `BlockArg::Value(v)`.
- `StackSlotData::new(StackSlotKind, size, align_shift)` — три аргумента.
- `isa_builder.finish(flags)` требует `Flags` и возвращает `Result`.

## 4. Скорость — главное разочарование

| Этап | Время |
|---|---|
| Мой фронтенд (`check`, без сборки) | < 0.01 с |
| **Полный цикл Keel сейчас** (фронтенд + C + gcc + запуск) | **0.03 с** |
| Только gcc на сгенерированном C | ~0.03 с |
| **Cranelift: только кодогенерация** (AOT) | **~0.002 с** |

Cranelift кодогенерирует примерно в **15 раз** быстрее gcc. Но сравнивать
надо не с Cranelift, а с **полным циклом моего компилятора**:

- сейчас весь цикл — 30 мс;
- из них фронтенд — доли миллисекунды;
- остальное — gcc.

То есть абсолютный выигрыш от перехода — **десятки миллисекунд**, а не
порядок величины. Я обосновывал переход скоростью — и в абсолютных цифрах
это слабый аргумент.

**Вывод.** Скорость компиляции не должна быть главным доводом за Cranelift
в Keel. Главный довод — другой, см. следующий раздел.

## 5. Что даёт Cranelift на самом деле

### Своя семантика вместо неопределённого поведения C

Сейчас Keel наследует от C всё, что C не определяет:

- порядок вычисления аргументов (`f(a(), b())` — какой раньше? в C
  неопределён);
- поведение при переполнении `int`;
- неинициализированная память.

Язык, обещающий безопасность памяти, не может оставлять это
неопределённым. С Cranelift я определяю эти вещи сам.

### Своя диагностика

Ошибки приходят от gcc словами gcc: «declaration of 'empty' as array of
voids». Для пользователя Keel это нечитаемо — такое приходится
перехватывать и переводить.

### Меньше слоёв

У LLVM несколько слоёв IR (LLVM IR → SelectionDAG → Machine IR), у
Cranelift — **один**. Это и делает его проще: не нужно проходить
конвейер трансформаций.

### `cranelift_frontend::SSABuilder` — автоматическая сборка SSA

Отдельная находка, и она важная. В `cranelift-frontend` есть `SSABuilder`
и обёртка `FunctionBuilder` с методами `use_var` / `def_var`:

```rust
let total = b.declare_var(types::I64);   // переменная уровня языка
let zero = b.ins().iconst(types::I64, 0);
b.def_var(total, zero);                   // определение
...
let hi = b.use_var(i);                    // использование
```

Компилятор сам разводит определения по блокам, ставит параметры блоков и
подставляет аргументы в `jump`/`brif`. То есть **самую трудную часть
миграции — построение SSA из дерева с переприсваиваниями — можно не делать
руками**.

Проверено на практике: `experiments/clif/src/bin/auto_ssa.rs` — та же
функция `sum_sq`, собранная через `use_var`/`def_var`. Результат тот же
(30), CLIF корректный:

```
block1(v2: i64, v16: i64):
    v5 -> v2
    v6 -> v16
    v15 -> v16
    v3 = iconst.i64 4
    v4 = icmp ult v2, v3
    brif v4, block2, block3
```

Видно, как SSA-механизм сам протащил `total` и `i` через цикл: в блоке
заголовка появились параметры `v2` и `v16`, а в блоке выхода — `v15`.

### Сколько это экономит

| | Ручной SSA | Автоматический SSA |
|---|---|---|
| Тело `sum_sq` | 52 строки | ~45 строк |
| Нужно знать | блочные параметры, аргументы `jump`/`brif`, соответствие типов | только `declare_var` / `def_var` / `use_var` |

Экономия в коде умеренная (около 15%), но **качественная разница
существенна**: ручной вариант требует от автора кода знать устройство SSA
и руками следить за соответствием типов аргументов блокам. Автоматический
вариант выглядит почти как исходный код на Keel.

Для Keel это означает: **переход на Cranelift не обязан означать «написать
свой SSA-конструктор»**. Скорее всего, достаточно взять `SSABuilder` и
скормить ему AST Keel.

### Обязательные детали API (0.137)

- `use_var`/`def_var` требуют, чтобы переменная была объявлена через
  `declare_var(ty)` — иначе паника.
- `finalize(frontend_config)` **обязателен** в конце функции: он проверяет
  (в debug), что все блоки запечатаны и заполнены, и сбрасывает
  состояние контекста.
- Блоки нужно запечатывать (`seal_all_blocks()` или `seal_block`).
- `jump`/`brif` вызываются с **пустым** списком аргументов:
  `b.ins().jump(block1, &[])` — SSA-аргументы подставляются сами.

## 6. Что делаем

**Пока оставляем C-backend.** Причины:

1. Мы проверяем **идею языка**, а не бэкенд. Тратя месяц на
   Cranelift-бэкенд, я отстану от проверки group borrowing.
2. Фронтенд всё равно меняется (см. список долгов в `lang-design.md`),
   а кодогенерацию переписывать дважды невыгодно.
3. Прикладные примеры уже дали кучу находок — и все они про фронтенд,
   не про бэкенд.

**Переход на Cranelift — пункт 6 в разделе 7.2 `docs/lang-design.md`**,
когда фронтенд устоится.

**Пока чиним границу с C**: переводим ошибки gcc в диагностику Keel с
указанием строки исходника. Дёшево, снимает самый неприятный симптом.

## 7. Как запустить эксперимент

```sh
cd ~/keel/experiments/clif
cargo run
```

Выведет CLIF, время кодогенерации и результат:

```
AOT Cranelift: 2.03ms, объектный файл 832 байт
main() вернул: 30
ожидалось: 30 (1+4+9+16)
```

Отдельный каталог `experiments/` со своим `Cargo.toml` и `[workspace]` —
он не собирается вместе с основным компилятором и не мешает `cargo test`.
