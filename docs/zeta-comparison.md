# Zeta: что проверено, что стоит взять, что — нет

**Зачем этот документ.** Zeta (github.com/murphsicles/zeta) — единственный
язык, который претендует на ту же цель, что и Keel: безопасная память +
простой синтаксис + быстрая компиляция. Когда проект упоминают, его
маркетинговые формулировки принимают за факты. Здесь — что проверено по
репозиторию, что из этого следует и что мы берём.

**Дата проверки.** Ноябрь 2026. Проверено по репозиторию на коммите
`ec83f3f8` (= v1.0.23 плюс один коммит обновления бинарника).

---

## 1. Что это за проект

- Лицензия MIT, 87 звёзд, 1481 файл, активно коммитится.
- Язык спроектирован «с нуля» на алгебраических основаниях
  Александра Степанова (*Elements of Programming*).
- Свой компилятор, своя стандартная библиотека, бэкенд — LLVM IR.
- Три языка в репозитории: Zeta (`.z`), C (рантайм), Rust (бутстрап).

### Что реально сделано

| | |
|---|---|
| `main` | **Чистый Zeta.** 52 файла `.z` в `src/`, ни одного `.rs`, нет `Cargo.toml` |
| `bootstrap` | Rust-реализация: 361 файл `.rs` + 126 `.z` |
| История | Начинается 21 марта 2026 с коммита «v0.3.7: Final Rust bootstrap…» |
| Теги | Старейший — `v0.6.0`. **Тега `v0.3.0` не существует**, вся линейка 0.1–0.5 отсутствует |

Про ключевой переход:

```
2026-04-15  ac6e353ea0  Remove Rust source files, keep only Zeta code
2026-05-03  fc64fb8176  Remove publish.yml workflow — Rust bootstrap removed
2026-05-04  ea799bc468  Fix CI: switch main to bootstrap branch
                        (main is Pure Zeta, no Cargo.toml)
2026-05-05  4165686ff3  Restructure branches: bootstrap = Rust snapshot,
                        dev = pure Zeta fork of main
```

**Вывод: заявление «Rust-бутстрап удалён, `src/` — чистый Zeta» для
ветки `main` — правда.** Rust-реализация намеренно живёт на ветке
`bootstrap` как снапшот, и CI собирает из неё релизные бинарники, потому
что на `main` строить нечем. Это обычная схема для self-hosted языка, а
не недоделка.

**Но.** Релизные бинарники содержат 20 370 Rust-символов и 9 Zeta-символов
— то есть публикуемый `zetac` собран **rustc**, а не Zeta.

**И ещё.** `.z`-перевод на `main` **отстаёт** от Rust-оригинала. Пример:
`comptime` в Rust-версии парсится и имеет флаг в AST, а в `.z`-файлах
`main` — ноль вхождений. Так что «язык компилирует себя» — направление
движения, а не достигнутое состояние.

### Чего нет в репозитории

- `install.sh` и `install.ps1`, на которые ссылаются примечания к
  релизу, — **404**. Быстрый установщик из примечаний не работает.
- У релиза v1.0.23 **ноль прикреплённых файлов**, хотя примечания
  ссылаются на четыре бинарника. Последний со скачиваемым — v1.0.21
  (13 скачиваний за полгода).

## 2. Бенчмарки: как их читать

Опубликованная таблица (v0.3.0, январь 2026):

| Бенчмарк | Zeta 0.3.0 | Rust 1.82 | Zig 0.13 | Go 1.23 | C++23 |
|---|---|---|---|---|---|
| Самокомпиляция | 14 мс | 3200 мс | 1800 мс | 4500 мс | 2800 мс |
| fib(40) итераций/с | 892 М | 840 М | 826 М | 263 М | 870 М |
| 100k актор пинг-понг | 0,94 мс | 1,41 мс | 1,12 мс | 2,8 мс | 1,08 мс |
| Hello world | ~7 кБ | ~280 кБ | ~12 кБ | ~2 МБ | ~12 кБ |

**Как это читать честно:**

- **«228× быстрее Rust» — некорректное сравнение.** Компилятор Zeta —
  18k строк, rustc — порядка миллиона. Плюс 3.2 с у Rust — это тёплая
  инкрементальная пересборка, а не полный бутстрап (тот занимает десятки
  минут). И сам тест относится к версии, которой в репозитории нет.
- **fib: 892M против 840M — разница 6%, в пределах шума.** Оба
  компилятора на пределе железа для наивного fib.
- **Акторы: 50% — правдоподобно**, для выделенного M:N-рантайма с
  зелёными потоками.
- **Размер hello world — реально значимо.** Причина понятна: у Zeta
  свой рантайм, у Rust — свой, у Keel пока glibc.

Итог: **абсолютные числа Zeta выглядят сильно, но сравнение некорректно.**
Сам по себе факт «14 мс на компиляцию настоящего компилятора» впечатляет —
просто не с чем сравнивать.

## 3. Что реально реализовано, а что нет

Проверено по коду. Важно: **реальная реализация — в Rust-версии**
(ветка `bootstrap`), `.z`-перевод на `main` отстаёт.

| Заявлено | Состояние |
|---|---|
| **Semiring-свёртки** | **Реально.** `SemiringOp` и `SemiringFold` — операторы MIR, `codegen.rs` их раскручивает |
| **Инварианты циклов** | **Реально.** `MirStmt::Invariant { cond, message }` — оператор MIR, раскручивается в код |
| **`comptime`** | **Реально** (в Rust-версии): парсер, флаг в AST, тесты `tests/comptime/` |
| **Концепты с наследованием** | **Реально.** AST, парсер, резолвер по `(concept, type)`, иерархия `concept ForwardIterator[T]: InputIterator[T]` |
| **`pre`/`post`** | **Реально** как операторы MIR (`MirStmt::Invariant` и аналогичные), то есть рантайм-проверки, а не доказательства |
| **`#[commutative]`, `#[associative]`, `#[identity]`** | **Атрибуты парсятся** (`tests/attribute-syntax/`), но **семантики нет**: переупорядочивания по ним в кодогенераторе не найдено. В `.z`-версии — только в примерах `src/correctness.z`, и этот файл **не подключён** к сборке компилятора |
| **Решётка `Regular→Semigroup→Monoid→Group→Ring`** | **Нет.** Есть перечисление конкретных операций (`SemiringOp`), но проверки «тип удовлетворяет структуре» нет. Это ручной набор, а не система |
| **CacheSafe TBAA / `noalias`** | **Не реализовано.** Флаг `cache_safe: bool` в `specialization.rs` есть, `noalias`/`tbaa` в кодогенераторе — ноль. Обещание «гарантирует отсутствие алиасинга, даёт векторизацию без `restrict`» не подкреплено |
| **Borrow checker «без borrow checker»** | Borrow checker **есть**: `src/frontend/borrow.z` (169 строк) — Rust-подобный трекер `Owned/Borrowed/MutBorrowed/Consumed` по переменным. Комментарий в коде: *«We'll need to adapt the borrow checker interface»* — переносили из Rust-версии, а не проектировали заново |
| **175+ кодов ошибок** | Заявлено в документации |
| **Тесты** | 951 файл тестов, **ни одного** на borrow/aliasing/move (три совпадения — про `type alias`, другое) |

### Общий вывод

**Замысел сильный, реализация — сильное подмножество, документация
опережает обе.**

Архитектурно всё на правильных уровнях: semiring и инварианты — операторы
MIR (их видит оптимизатор), comptime — флаг в AST, концепты — узлы AST с
резолвером. Это не «прикручено сбоку».

Но заявленная «встроенная формальная верификация», «решётка уточнения
концепций» и «CacheSafe TBAA» — **уровень «проект на год вперёд описан в
readme»**.

## 4. Что берём в Keel

### 4.1. Берём

**Диагностика с кодами и подсказками.** У Zeta 175+ кодов с объяснением
и предложением исправления. Keel это нужно **больше**: у него есть
ошибки, которых нет ни у кого, — инвалидация ссылки, нарушение
`mut`-контракта, move из элемента коллекции. Их нельзя объяснить одним
словом «нельзя», надо сказать *почему* и *что делать*.

Формат для Keel: **код + причина (какое правило и где) + путь (что
делать)**. Тогда и «цепочка инвалидации» закроется сама: не «ссылка
инвалидирована», а «`book.entries[0].hp` заменён на строке 42, вот эта
ссылка на него устарела».

**`if` как выражение.** Zeta: `let max = if a > b { a } else { b };`.
Убирает целый класс временных переменных. Дёшево, чисто.

**`for` по диапазонам и коллекциям.** У Keel только `while`. Реализуется
поверх `while` дёшево, **но** `for` по коллекции в Keel обязан обходить
*элементы* — а это ровно то, что требует group borrowing. То есть `for`
станет отличным тестом модели.

**`match` + `enum`.** В Keel нет ни того, ни другого. Это путь к
`Option`/`Result` — пункту 1 в списке долгов. Исчерпывающий `match` по
enum'у — дешевле, чем Option/Result-типы, и закрывает часть задачи.

**`pre`/`post` как ступень к `Option`/`Result`.** Контракты дешевле и
покрывают часть задачи: проверка предусловий на границе функции, с
сообщением вместо «`-1` значит ошибка». Позволяет **начать** решать
проблему, не переписывая типы во всём коде.

**Semiring-свёртка как примитив, а не как система законов.** В Keel
можно завести встроенную операцию:

```
fold_sum(a [int; N]) int    // компилятор знает: сложение целых ассоциативно
```

и разворачивать её в один проход с векторизацией — **без атрибутов и без
пользовательских утверждений**. Именно так это и работает в реальной
реализации Zeta, и именно поэтому примитивные операции безопасны.

**Собственный минимальный рантайм.** Нужен для: своего аллокатора →
поколений (`Gen<T>`) → варианта Б в п. 5 раздела 7.2; собственной
семантики вместо C; меньшего размера бинарника.

### 4.2. Не берём

**`#[commutative]` / `#[associative]` для пользовательских операций.**
Это утверждение программиста, которое никто не проверяет. Ошиблись в
атрибуте — компилятор перегруппирует вычисления и получит неправильный
результат. Это тихий баг оптимизации, худший его вид.

У Keel здесь **преимущество**: пути дают точную информацию об алиасинге
без доверия к пользователю. `&world.entities[0]` и `&world.entities[1]`
заведомо не пересекаются, и компилятор это знает.

**Решётку уточнения концепций.** Требует проверки «тип удовлетворяет
структуре» — это работа масштаба системы доказательств. Концепты как
таковые (имя + набор функций + наследование) — полезны и без алгебры.

**Borrow-модель Zeta.** Там Rust-правило «один писатель или много
читателей» — то есть ограничения Rust'а по построению. Keel снимает
это ограничение (две изменяемые ссылки на разные элементы), и в этом
Keel впереди. Копировать нечего.

**Неявный возврат по последнему выражению.** Zeta это допускает. Keel
явнее, и в этом его преимущество.

**Замыкания.** Полезны, но требуют вывода типов для лямбд — дорого.

### 4.3. Порядок

| # | Что | Почему | Стоимость |
|---|---|---|---|
| **1** | **Анализ выхода — закрыть дыру с висячими ссылками** | Это дыра в безопасности: ссылка в поле структуры может уехать из функции и стать use-after-free, и компилятор её пропускает. Не удобство, а корректность | День-два |
| 2 | `restrict` по путям | Данные уже есть, выигрыш сразу | 1 строка |

## 5. Синтаксис: `x int` или `x: int`?

Zeta использует `x: int` (Rust/TS/Kotlin/Swift/Pascal). Keel —
`x int` (как в Go).

**Решение: оставить `x int`.** Обоснования:

1. **Keel уже в согласии с Go** — вторым по популярности стилем
   объявлений. Это не экзотика.
2. **Свой синтаксис — не то, чем Keel отличается.** Его отличие —
   модель владения: одна ссылка вместо двух, пути вместо времён жизни,
   разрешение двух изменяемых ссылок на разные элементы.
3. **Добавление двоеточия дало бы три формы записи типов** вместо одной:

   ```
   let x int = 5;               // объявление
   fn f(x int) int              // параметр и возврат
   fn g(e in ents[]) mut(...)   // параметр-внутри и контракт
   ```

   Три формы — это не «согласованность», а «три согласованности».
   Вариант «`let x int` в объявлениях + `x: int` в аннотациях» — ещё
   хуже: один язык, две конвенции.

**Честный контраргумент:** если бы Keel проектировался с нуля сегодня,
двоеточие было бы лучше — привычность (Rust, TS, Kotlin, Swift, Pascal)
важнее единообразия с непривычным. Но переделка — это работа на неделю
(25 тестов, 4 примеда, документация, тур) ради косметики.

**Компромисс на будущее:** если синтаксис когда-нибудь будут менять —
менять целиком и сразу, и тогда отдельная задача с отдельным
обоснованием. Точечно вставлять двоеточие нельзя.

Отдельно: в Keel двоеточие **свободно** — оно есть в лексере, но не
используется ни парсером, ни AST. Так что технических препятствий нет,
есть только вопрос согласованности.
