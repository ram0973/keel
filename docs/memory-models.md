# Модели памяти: обзор подходов

Записано по итогам разбора: как разные языки решают одну и ту же задачу —
безопасно и предсказуемо управлять памятью, не платя за это больше, чем
нужно. Документ не про Keel напрямую, а про пространство решений, из
которого Keel выбирает. Сводка для Keel — в конце.

## 0. Проблема

Любой язык с кучей отвечает на три вопроса:

1. **Когда освобождать?** Сразу (детерминизм) или когда-нибудь (GC).
2. **Кто владеет?** Один, много, никто — и как это проверяется.
3. **Что делать с циклами и висячими ссылками?** Ловить статически,
   рантаймом или не ловить вовсе.

Ответы образуют спектр: от «всё руками» (C) до «память невидима»
(Roc/Haskell). Ни один ответ не лучше всех — каждый меняет цену.

## 1. Спектр подходов

| Язык | Модель | Детерминизм | Циклы | Проверка владения | Цена |
|---|---|---|---|---|---|
| C | ручное | да | утечка/UB | нет | нулевая, но баги |
| C++ | RAII + smart pointers | да | утечка (`shared_ptr`) | нет (дисциплина) | нулевая при умении |
| Rust | владение + borrow checker | да | утечка (`Rc`) | да, статически | нулевая в рантайме |
| C# | tracing GC | нет (паузы) | собирает | нет | паузы, память |
| Swift | ARC | да | утечка (`weak`) | частично (exclusivity) | refcount-трафик |
| Roc | refcount + FBIP | да | почти невозможны | нет | refcount-трафик |
| Nim | ORC (ARC + циклы) | да | собирает | частично (`sink`/`lent`) | refcount + сборщик |
| Valen | group borrowing | да | — | да (группы) | нулевая |
| Koka | Perceus refcount | да | cycle collector | нет | refcount |
| Hylo | value semantics | да | — | нет (exclusivity) | нулевая |
| ECS/SlotMap | generational keys | да | — | нет (ключи) | индирекция |

Дальше — разбор каждого подхода и его минусов.

## 2. ECS / SlotMap / поколенческие арены

Идея поколенческих арен лежит в фундаменте современных ECS (Entity
Component System) — на нём построены Bevy (Rust), Flecs (C/C++), Unity DOTS.

### Как это работает

- **Entity = поколенческий ключ** `(index, generation)`. Создание сущности
  не выделяет объект в куче — берётся свободный индекс из пула. При
  удалении слот освобождается, поколение увеличивается, и старые ключи
  `(42, 1)` перестают быть валидными: новый жилец слота 42 — это `(42, 2)`.
- **Components = параллельные плоские массивы** (SoA). Свойства хранятся
  отдельно от Entity, сгруппированы по типам.
- **Systems = линейные циклы** по нужным массивам.

### Две организации хранения

1. **Sparse sets** (EnTT): разреженный массив индексируется по `index`,
   хранит позицию в плотном массиве + поколение; плотный массив хранит
   сами компоненты без дыр. Удаление — `swap_remove`.
2. **Archetypes** (Bevy, Flecs): сущности с одинаковым набором компонентов
   лежат в одной таблице-архетипе, каждый компонент — непрерывная колонка.
   Таблица маршрутизации `location_map[index]` за O(1) даёт (архетип, строка).

### Плюсы

- Нет ссылок и графов объектов: связи — только копируемые ключи (8 байт).
- Линейный обход колонок — идеальная локальность, автовекторизация.
- Планировщик знает, какие системы читают/пишут какие колонки, и запускает
  непересекающиеся параллельно без мьютексов.

### Минусы

1. **«Нет cache miss» — только для линейного обхода.** Переход по ключу —
   это `location_map[index]` → `(архетип, строка)` → `column[row]`: две-три
   **зависимые** загрузки, каждая — вероятный промах. Sparse set — то же:
   `sparse[idx]` → `dense[pos]`. ECS оптимизирует обход, а не навигацию.
2. **Структурные изменения дороги.** Добавить/убрать компонент = переселить
   сущность в другой архетип: скопировать все компоненты, обновить
   `location_map`, `swap_remove` в старой таблице. Тег, дёргающийся каждый
   кадр, — трэшинг между архетипами.
3. **Нельзя менять состав во время итерации.** Отсюда command buffers
   (отложенные spawn/despawn/add/remove) — ещё слой сложности и багов.
4. **Детерминизм.** Параллельные системы по умолчанию выполняются в
   недетерминированном порядке; для реплеев/сети/отладки нужны явные
   constraints.
5. **Параллелизм грубый.** Планировщик знает типы компонентов, а не
   сущности: две системы, пишущие в `Position` разных сущностей, конфликтуют.
6. **Ключ — не указатель.** `enemy.health -= 10` не работает: нужен запрос,
   компонент должен существовать.
7. **Иерархии, графы, UI не ложатся.** Сцена-граф, parent-child, дерево UI —
   в чистом ECS неудобны; Bevy добавляет `ChildOf`/`Children`, Flecs —
   relations, но обход дерева снова навигация по ключам.
8. **Память под карты.** Sparse-массив по `index` большой при разреженных
   индексах; `location_map` — O(max_entities); 8 байт ключа в каждом месте.
9. **Переполнение поколения (ABA).** `gen: u32` переполняется после 2³²
   переиспользований слота — старый ключ снова «валиден». Это runtime-проверка,
   а не статическая гарантия.
10. **Сериализация и сеть.** Сырой `(index, gen)` не стабилен между
    запусками; для сейвов и сети нужны стабильные ID или ремаппинг.
11. **Сложность и отладка.** Системы, запросы, планировщик, command buffers —
    много машинерии; для 500 объектов это оверкилл. Данные отвязаны от
    личности, стек-трейсы ведут в дженерик-код запросов.

**Итог.** ECS выигрывает на многих однородных сущностях и горячем линейном
обходе (физика, партиклы, толпы). Проигрывает на индивидуальном поведении,
иерархиях и простоте. Тот же компромисс, что `Gen<T>` в Keel: безопасный
ключ вместо указателя — ценой индирекции и ручного управления ареной.

## 3. Swift: ARC + value semantics

### Модель

- `struct`/`enum` — значимые типы, копируются, COW для `Array`/`String`/
  `Dictionary` (буфер общий, пока не мутируешь).
- `class` — ссылочный тип в куче с **ARC**: компилятор вставляет
  `retain`/`release`, объект умирает при счётчике 0.

### Плюсы

- Детерминизм: нет пауз GC, `deinit` сразу.
- Значимые типы дают Rust-подобную семантику без borrow checker.
- `weak`/`unowned` для разрыва циклов.
- Swift 5.9+ — `~Copyable` (move-only), `borrowing`/`consuming` параметры.
- `inout` + exclusivity: одновременный доступ к переменной — ошибка
  компиляции или runtime-trap. Лёгкий borrow check.

### Минусы

- ARC не бесплатен: `retain`/`release` — трафик, счётчики **атомарные**.
- Циклы `class`-ов текут без `weak`.
- `weak` медленный (side tables), `unowned` — «поверь мне».
- Полного borrow checker нет → гонки данных возможны; ловятся
  `Sendable`/actors, но это не проверка владения.
- Производительность классов непредсказуема: цепочки retain/release.

**Урок.** Можно далеко уехать на значимых типах + ARC без borrow checker.
Цена — refcount-трафик и циклы. `~Copyable` — доказательство, что
move-семантику можно добавить точечно.

## 4. Roc: refcounting + opportunistic mutation

### Модель

Чисто функциональный язык (Elm-подобный), значения иммутабельны. Память —
подсчёт ссылок, вставленный компилятором. Ключевая оптимизация —
**opportunistic mutation**: если refcount == 1, значение мутируется на месте
вместо копирования. Тот же приём, что Perceus reuse в Koka и `inout` в Hylo
(FBIP — Functional But In-Place).

### Плюсы

- Нет tracing GC, нет пауз, детерминизм.
- Нет borrow checker и аннотаций — о памяти не думаешь.
- Циклы почти невозможны: нет мутабельных ссылок и ленивости.
- **Platform-модель**: аллокатор и рантайм предоставляет хост (Rust/Zig/C/WASM).
- Иммутабельность + tag unions (`Result`, без `null`) убирают класс ошибок.

### Минусы

- Refcount-трафик есть; opportunistic mutation срабатывает не всегда.
- Pre-1.0, экспериментальный, маленькая экосистема, API плывёт.
- Функциональная парадигма: нет мутабельных ссылок, графы/игры — не ниша.
- Отладка производительности сложнее: «почему копия, а не мутация?».
- Platform-модель — переносимость ценой зависимости рантайма от хоста.

**Урок.** Противоположный полюс: не управляй памятью вообще, компилятор
вставит refcount и мутирует на месте, когда безопасно. Работает только
потому, что язык иммутабельный. Для императивного Keel с `&T` и `mut` этот
путь не подходит напрямую — но `opportunistic mutation` = ровно идея
«освобождать/мутировать, когда владелец один», которую Keel уже использует
в liveness-освобождении `Vec`.

## 5. Полная иммутабельность — перерасход памяти?

Короткий ответ: **сама по себе — нет. Наивная — да.** Всё решает, что
компилятор/рантайм делает с уникальностью значения. «Полная иммутабельность
без оптимизаций» — соломенное чучело: ни один продакшн-язык так не работает.

### Три механизма, убирающие перерасход

1. **Structural sharing (persistent structures).** Новая версия делит почти
   всё со старой. Persistent-список: `prepend` O(1), хвост общий.
   Persistent-вектор (Clojure RRB-tree), HAMT: обновление O(log₃₂ N).
   M версий списка из N элементов = N + M узлов, а не N·M.
2. **COW.** Пока владелец один — общий буфер; при мутации после шаринга —
   копия. Swift `Array`, Rust `Cow`/`Arc::make_mut`.
3. **FBIP / uniqueness (refcount == 1 → мутировать на месте).** Koka Perceus,
   Roc opportunistic mutation. Единственный владелец — копии нет.

| Подход | Обновить 1 элемент | Память на N версий | Кэш |
|---|---|---|---|
| Наивная копия | O(N) | O(N·M) | плохо |
| Persistent (sharing) | O(log N) | O(N + M·log N) | средне |
| COW | O(1), пока один | зависит от шаринга | хорошо, пока один |
| FBIP (refcount==1) | O(1) in-place | O(N) | отлично |

### Где перерасход реально есть

- **Много мелких узлов.** Persistent-список/дерево: заголовок (refcount +
  тег) + указатели на каждый элемент. Для списка `int` ~24–32 байта на
  элемент против 8 в плоском массиве — 3–4×. Плюс pointer chasing.
- **Refcount-заголовки.** 8 байт на каждый объект в куче.
- **Boxing.** Иммутабельные языки часто пакуют всё в кучи — выбор реализации,
  а не следствие иммутабельности.
- **Аллокационный churn.** Много короткоживущих узлов → давление на аллокатор.
- **Сохранённые старые версии.** Память растёт — но это фича persistence
  (undo, снапшоты), а не утечка.

### Где иммутабельность экономит

- **Шаринг версий** — главный выигрыш: две версии 1M-элементного списка,
  отличающиеся одним элементом, делят 999 999 узлов.
- **Interning / hash-consing** — одинаковые значения хранятся один раз.
- **Нет защитных копий.** В мутабельном коде часто копируют «на всякий
  случай»; иммутабельность снимает необходимость.
- **Проще GC** — нет write barriers, меньше мутаций.

### Настоящая цена — чаще время и кэш, чем байты

Для «одна текущая версия, много мутаций» persistent-структуры дороже
плоского мутабельного массива и по памяти, и по скорости. Для «много
версий / шаринг / уникальный владелец» — дешевле или наравне. Поэтому FBIP
и uniqueness-анализ — не украшение, а то, что делает иммутабельность
практичной.

### Примеры

- **Haskell** — главный виновник перерасхода не иммутабельность, а
  ленивость (thunks, замыкания) и boxing.
- **Clojure** — persistent vector/map (RRB/HAMT): умеренный перерасход,
  отличный шаринг.
- **Elm/Roc** — refcount + FBIP: копия только когда значение разделено.
- **Swift** — COW-массивы: бесплатно, пока не расшарил.
- **Rust** — `im`, `rpds`: persistent-структуры явно, когда нужны.

## 6. Swift 6: циклы и refcount

### ARC не менялся — циклы всё ещё текут

Swift 6 — прежде всего **data-race safety**: строгая проверка `Sendable`,
изоляция акторов, `async`/`await`, typed throws. Модель памяти та же ARC.
Циклового коллектора не появилось.

- `class A { var b: B? }` ↔ `class B { var a: A? }` — течёт, как в Swift 5.
  Нужен `weak`/`unowned` на одной стороне.
- Классика — замыкание, захватившее `self` сильно: `self.handler = { self.update() }`.
  Лечится `[weak self]`.
- `Unmanaged`, C-interop, `withUnsafe...` — можно утечь руками.
- `deinit` не вызывается у утёкшего объекта — способ ловить.

Что нового в 6.x по памяти (не про циклы):

- **`~Copyable`** (move-only) — без refcount, с `deinit`, `consuming`/`borrowing`.
- **`Span`** — заимствованный непрерывный кусок памяти без refcount.
- **`InlineArray`** — массив фиксированного размера на стеке, без кучи.
- Строгая конкурентность предотвращает гонки, но не утечки.

### Refcount — да, замедление, но точечное

ARC вставляет `retain`/`release` на этапе компиляции. Дорогая часть — не
пара, а **атомарный read-modify-write** счётчика и барьеры памяти.

Где болит:

- Горячие циклы с `class` — retain/release на каждой итерации.
- Передача объектов через границы функций — пары retain/release.
- `weak` — side table, заметно медленнее.
- Контеншн: один объект дёргают несколько ядер — cache line bouncing.
- Коллекции классов — каждый элемент удерживается.
- Замыкания, захватывающие объекты.

Где не болит:

- `struct`/`enum` — refcount нет (если внутри нет класса или COW-буфера).
- COW-буферы — одна проверка `isKnownUniquelyReferenced` на мутацию.
- `~Copyable` — refcount нет вообще.
- `borrowing`-параметры — без retain/release для чтения.
- `Span`/`InlineArray` — без кучи и счётчиков.

Оптимизации: ARC-оптимизатор выкидывает избыточные пары;
`withExtendedLifetime`, `withoutActuallyEscaping`; `borrowing`/`consuming`
убирают лишние счётчики на границах.

### ARC vs tracing GC

| | ARC (Swift) | Tracing GC (C#/Go/Java) |
|---|---|---|
| Паузы | нет | есть |
| Детерминизм | да (`deinit` сразу) | нет |
| Стоимость | на каждую операцию (атомики) | амортизированная, throughput |
| Память | ниже (нет резерва под GC) | выше (heap, фрагментация) |
| Циклы | текут | собираются |
| Худший случай | контеншн на счётчике | длинная пауза |

Для latency-sensitive (UI, аудио, игры) ARC обычно выигрывает. Для
allocation-heavy throughput (серверные батчи) GC может быть быстрее:
bump-allocation и никакого refcount-трафика.

## 7. Swift 6 vs Rust

Разные ответы на один вопрос: «как гарантировать безопасность памяти и
гонок». Rust доказывает всё статически и бесплатно; Swift 6 проверяет часть
статически, часть — рантаймом (ARC, exclusivity), и добавляет move-only
типы как опцию.

| Ось | Rust | Swift 6 |
|---|---|---|
| Память | владение + borrow checker, lifetimes | ARC + value types + `~Copyable` |
| Гарантия | compile-time, zero-cost | compile-time (частично) + runtime |
| Циклы | текут (`Rc`), но `mem::forget` — safe | текут (`class`), нужен `weak` |
| Конкурентность | `Send`/`Sync`, `async` (tokio и др.) | `Sendable`, actors, `async` (встроенный) |
| Гонки данных | статически (`Send`/`Sync`) | статически (`Sendable` + actor isolation) |
| Runtime | нет (кроме `std`) | есть (ARC, executor) |
| Производительность | zero-cost, предсказуемая | ARC-оверхед, value types близко |
| Кривая обучения | крутая | пологая, но concurrency-аннотации |
| Экосистема | широкая, кросс-платформенная | Apple-centric, растёт |
| Компиляция | медленная | медленная |
| FFI | C, bindgen | C/C++/ObjC, `@objc` |

### Память и владение — главное различие

**Rust.** Владение, `&T`/`&mut T`, lifetimes. Алиасинг XOR мутабельность
доказано компилятором. Нет рантайма, нет refcount по умолчанию. Move по
умолчанию. Цена — сложность и время компиляции.

**Swift 6.** ARC + значимые типы. `inout` + exclusivity — лёгкий borrow
check: очевидные случаи ловятся компилятором, остальные — runtime-trap.
`~Copyable` — опциональный Rust-подобный владелец. Lifetimes нет,
статической проверки алиасинга нет.

Разница в философии: Rust не даёт написать гонку/висяк; Swift даёт, но
ловит часть в рантайме и полагается на ARC. Циклы в обоих текут, но по
разным причинам: Rust — `Rc`-цикл (safe leak), Swift — `class`-цикл без `weak`.

### Конкурентность

**Rust.** `Send`/`Sync` — маркерные трейты, проверяются статически.
`Arc<Mutex<T>>`, каналы, `async`/`await` без встроенного runtime — выбираешь
tokio/async-std/smol. Гонки данных невозможны в safe-коде; дедлоки и
логические гонки — возможны.

**Swift 6.** Строгая конкурентность по умолчанию: `Sendable`, изоляция
акторов, `@MainActor`, structured concurrency, typed throws. Встроенный
cooperative executor. Гонки ловятся статически через `Sendable`/actor
isolation. Акторы дают сериализацию без мьютексов, но появляются reentrancy
и actor hop overhead.

### Производительность

- **Rust** — zero-cost абстракции, нет runtime, нет refcount по умолчанию,
  предсказуемый код. Лучше для систем, embedded, WASM, крипто, сетей, движков.
- **Swift** — ARC-трафик, но `struct`/`enum`/`~Copyable`/`Span`/`InlineArray`
  сокращают его до почти нуля в горячем коде. Для прикладного — близко; для
  жёсткого системного — Rust впереди.

### Где кто выигрывает

- **Rust**: системное ПО, embedded, WASM, высоконагруженные сервисы, движки,
  крипто, всё, где нужен контроль и нет runtime.
- **Swift 6**: приложения Apple, UI, быстрая разработка, код с сильной опорой
  на значимые типы, серверный Swift (Vapor), embedded-подмножество.

## 8. C++

Противоположный Rust полюс: ручное управление + RAII + умные указатели,
безопасность не гарантирована. «C с деструкторами и шаблонами», а не «Rust
без borrow checker».

### Модель памяти

- **RAII**: деструкторы, детерминированное освобождение на стеке.
- **`unique_ptr`** — эксклюзивное владение, move-only, zero-overhead.
  Ближайший аналог Rust `Box`.
- **`shared_ptr`** — refcount в control block, атомарный. Аналог `Arc`, но
  явный. `make_shared` кладёт объект и control block в одну аллокацию.
- **`weak_ptr`** — разрыв циклов, аналог `Weak`.
- Сырые указатели/ссылки — без владения и проверок.

Циклы `shared_ptr` текут — ровно как `Rc` в Rust и `class` в Swift.

### Владение и move

- Move-семантика (`std::move`, rvalue references) есть, но moved-from объект
  остаётся валидным в неопределённом состоянии — использовать компилятор не
  запрещает. В Rust move проверяется компилятором.
- Rule of 0/3/5: копирование/перемещение/деструктор — руками.
- Нет lifetimes, нет проверки алиасинга. `&` в C++ — Rust `&` без проверки
  времени жизни.

### Безопасность

- UB везде: висячие указатели, use-after-free, double-free, переполнение
  буфера, неинициализированное чтение, гонки данных.
- `std::vector::operator[]` не проверяет границы; `.at()` — проверяет.
- `std::span` (C++20) — невладеющий вид, по умолчанию без проверки.
- Санитайзеры (ASan, UBSan, TSan, MSan) — обнаружение, не предотвращение.
- Core Guidelines + `gsl` + статический анализ (clang-tidy, PVS-Studio) —
  дисциплина, не гарантия.
- Contracts (C++26, P2900): `pre`, `post`, `contract_assert` — реализация
  ещё не везде.
- Profiles (предложение Страуструпа) — «безопасные профили», спорно.
- `std::optional`/`variant`/`expected` (C++23) — Option/enum/Result-подобные,
  но без проверки исчерпываемости.

### Конкурентность

- `std::thread`, `std::mutex`, `std::atomic`, `condition_variable`,
  `std::jthread` (C++20, auto-join).
- Нет `Send`/`Sync` — гонка данных это UB, а не ошибка компиляции.
- Coroutines (C++20) — низкоуровневые, нужна библиотека.
- Встроенного async-runtime нет.

### Производительность

- Zero-cost абстракции при умении: `unique_ptr` бесплатен, шаблоны
  разворачиваются, нет runtime.
- `shared_ptr` — атомарный refcount, overhead как у ARC.
- Полный контроль: кастомные аллокаторы, placement new, арены, пулы.
- Может быть быстрее Rust в отдельных бенчмарках за счёт зрелости
  оптимизаторов, но менее предсказуем по безопасности.

### Сравнение

| Ось | C++ | Rust | Swift 6 | C# |
|---|---|---|---|---|
| Память | RAII + smart pointers | владение + borrow checker | ARC + value types | tracing GC |
| Безопасность | не гарантирована (UB) | safe by default | safe + runtime checks | safe by default |
| Циклы | текут (`shared_ptr`) | текут (`Rc`) | текут (`class`) | собираются |
| Move | есть, moved-from usable | есть, compile-checked | `~Copyable` (opt-in) | нет (ref) |
| Гонки | UB | `Send`/`Sync` | `Sendable`/actors | lock-based, без статики |
| Runtime | нет | нет | есть | есть (GC) |
| Zero-cost | да (при умении) | да | частично | нет |
| Сложность | огромная | высокая | средняя | средняя |

**Выигрывает:** HPC, игры (Unreal), браузеры, ОС, ML-фреймворки (ядро
PyTorch/TensorFlow — C++), embedded, всё, где нужен контроль, ABI-стабильность
и зрелые библиотеки (Boost, Qt).

**Проигрывает:** безопасность (UB, висяки, гонки), сложность языка, время
компиляции, эргономика. Нет статических гарантий владения/алиасинга.

## 9. Nim

«Python-подобный синтаксис, C-производительность, несколько стратегий
памяти». По умолчанию с Nim 2.0 — **ORC**: ARC + сборщик циклов. Ближе
всего к «Swift, который умеет собирать циклы».

### Стратегии памяти (`--mm:`)

- **`orc`** (по умолчанию с 2.0) — ARC + trial-deletion cycle collector
  (Bacon–Rajan). Детерминизм для ацикличных данных, циклы собираются.
- **`arc`** — чистый refcount, без сборщика циклов. Циклы текут.
- **`refc`** — старый дефолт: отложенный refcount + сборщик циклов.
- **`none`** — ручное управление (embedded, ядра).
- **`boehm`**, **`markAndSweep`** — tracing GC.

### ORC подробнее

- **Cursor optimization**: компилятор выводит «заимствованные» ссылки
  (`{.cursor.}`), которые не трогают refcount. Rust-подобное `&T`, но
  выведенное, а не аннотированное.
- **Хуки**: `=destroy`, `=copy`, `=sink`, `=trace`, `=wasMoved` —
  пользователь определяет копирование/уничтожение.
- **`sink`** — потребляющий параметр (Rust move), **`lent`** — заимствованный
  (Rust `&T`), **`var`** — мутабельный заимствованный (Rust `&mut T`),
  **`move(x)`** — явный move.
- Циклы собираются trial deletion: сборщик временно «обнуляет» счётчики и
  смотрит, что осталось достижимым. Дороже ARC, но без пауз tracing GC.

### Владение

Есть `sink`/`lent`/`var`/`move` — лёгкие аннотации владения. Но полного
borrow checker нет: висячие `ptr`, use-after-free через `cast`/`addr`,
гонки — возможны. «Rust-подобные инструменты без Rust-подобных гарантий».

### Безопасность

- Проверки границ, `nil`, переполнения — включены в debug, выключаются в
  `-d:release`/`-d:danger`.
- `ref` — refcounted, безопаснее; `ptr` — сырой, опаснее.
- Escape hatches: `ptr`, `cast`, `unsafeAddr`, `{.unsafe.}`.
- `{.experimental: "strictFuncs".}` — ограничение побочных эффектов.
- Нет lifetimes, нет статической проверки алиасинга.

### Конкурентность

- `--threads:on`, `Thread[T]`, `Channel[T]`, `Lock`, `Cond`, `std/atomics`.
- **`Isolated[T]`** — тип, который можно безопасно перемещать между потоками
  (аналог `Send`, но опциональный).
- `asyncdispatch` — однопоточный event loop, `Future[T]`, `async`/`await`.
- Полной проверки гонок данных нет — `Isolated` помогает, но не гарантирует.

### Производительность

- Компилируется в C (или C++, JS, LLVM через `nlvm`).
- Zero-cost абстракции, нет runtime (при `arc`/`orc`/`none`).
- ARC/ORC-оверхед есть, но cursor optimization его режет.
- `--mm:none` — для embedded и ручного контроля.
- Близко к C, местами быстрее Go.

### Сравнение

| Ось | Nim | Rust | Swift 6 | C++ | C# |
|---|---|---|---|---|---|
| Память | ORC (ARC+циклы), arc, refc, none | владение | ARC | RAII+smart ptr | tracing GC |
| Безопасность | checks + escape hatches | safe by default | safe + runtime | UB | safe by default |
| Циклы | ORC собирает | текут (`Rc`) | текут | текут | собирает |
| Move | `sink`/`move` | compile-checked | `~Copyable` | moved-from usable | нет |
| Гонки | `Isolated`, без полной проверки | `Send`/`Sync` | `Sendable`/actors | UB | lock-based |
| Runtime | нет (C backend) | нет | есть | нет | есть |
| Zero-cost | да | да | частично | да | нет |
| Синтаксис | Python-подобный | Rust | Swift | C++ | C# |

**Выигрывает:** быстрая разработка с C-производительностью,
метапрограммирование (макросы, шаблоны, `compileTime`), кросс-компиляция
через C, embedded (`--mm:none`), скрипты, CLI, Python-интероп (`nimpy`).

**Проигрывает:** экосистема меньше Rust/Go/C++; нет статических гарантий
владения; ORC-сборщик циклов — дополнительная сложность; сообщество
небольшое; «магия» метапрограммирования затрудняет чтение.

## 11. Что из этого для Keel

Keel выбрал **путь Rust** — статическая проверка заимствований на путях,
`&T`, `mut`-контракты, zero-cost. Это ядро идеи. Но обзор даёт несколько
конкретных уроков:

1. **`Gen<T>` — это ECS-ключ в миниатюре.** Тот же компромисс: безопасный
   ключ вместо указателя, ценой индирекции и ручного управления ареной.
   Минусы ECS (навигация по ключу, структурные изменения, ABA) применимы и
   к `Gen<T>` — их стоит держать в голове.

2. **Liveness-освобождение `Vec` — это FBIP.** «Мутировать/освобождать,
   когда владелец один, копировать/шарить, когда алиасится» — ровно идея
   Roc/Koka. Keel берёт выигрыш uniqueness-анализа, не платя за
   функциональную парадигму.

3. **Swift — альтернатива без borrow checker.** `~Copyable` показывает, что
   move-семантику можно добавить точечно; ARC — что можно жить без
   статической проверки, ценой refcount и циклов. Если статическая проверка
   Keel окажется слишком дорогой, это запасной путь.

4. **Nim — самый близкий по бэкенду (C) и по духу.** Особенно интересны:
   ORC (ARC + сборщик циклов), `sink`/`lent`/`var`/`move` как лёгкие
   аннотации владения, cursor optimization (автовыведение заимствований),
   хуки `=destroy`/`=copy`/`=sink` (пользовательские деструкторы, которых у
   Keel пока нет).

5. **C++ — полюс «ручное + RAII».** Идея «владение выражается типом»
   (`unique_ptr` vs `shared_ptr` vs сырой) — та же, что у Rust, но без
   проверки компилятором. Keel делает её проверяемой.

6. **Честная формулировка про «нет GC».** Как уже сказано в
   `keel-risks.md`: расходы Keel предсказуемы и малы, но не нулевые —
   bounds-check, рантайм-проверка generational references, память на пути
   для диагностики.

**Итог.** Пространство решений не имеет «лучшего» ответа. Rust — «докажи
безопасность, заплати сложностью»; Swift — «ARC + значимые типы + опциональный
move»; C++ — «максимум контроля, ноль гарантий»; Nim — «прагматичный
компромисс с ORC»; Roc — «память невидима, но только без мутабельных
ссылок»; ECS — «ключи вместо указателей». Keel стоит на Rust-полюсе
осознанно: статическая проверка там, где дёшево, рантайм-ключ там, где граф.

---

Не проверял: конкретные цифры overhead (ARC, ORC, persistent structures) —
это порядковые оценки по устройству рантаймов, не замеры; Swift 6 strict
concurrency включается по модулям, C++26 contracts/profiles ещё не устоялись,
Roc pre-1.0 — так что часть утверждений может устареть.
