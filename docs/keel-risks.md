# Keel — минусы, риски, подводные камни

Зафиксировано как часть дизайна, чтобы не переоткрывать при каждом решении.
Плюсы, с которыми согласны: отсутствие GC, малое потребление памяти,
несложный синтаксис. Оговорка к первому — в пункте 2.

## 1. Непроверенная в проде модель памяти (уточнено 2026-11 по репозиторию)

Group borrowing существует не только как черновик Ника Смита: это работающий
компилятор (~2600 строк borrow checker'а), компилируемый в LLVM IR, с
интеграцией с Rust через пропатченный rustc. Автор потратил на это около года.
То есть идея доказана в смысле «она реализуема и работает».

Но фактическое состояние (проверено по репозиторию valen-lang/valen):

- версия 0.1.0 — ни тегов, ни релизов на GitHub нет вообще;
- README: «всё ещё прототип, едва перешагнувший стадию proof-of-concept»,
  а 0.1 — это то, что ещё предстоит выпустить;
- репозиторий создан 2026-08-15, последний push 2026-10-18;
- borrow checker **полностью переписан 2026-10-17** на новый дизайн
  «Symphony V2» (обратный обход), то есть наша механика в реальной
  реализации отлаживается меньше месяца;
- `end_to_end_tests/tests/borrow_check_tests.rs` — 20 строк и **один** тест,
  причём проверяющий, что программа компилируется при выключенной проверке;
- из 181 тест-программы на языке большинство — проверки интеропа с Rust
  (54), строки (16), структуры (14); отдельной категории borrow-тестов нет.

Вывод: готового алгоритма, который можно взять и реализовать, нет —
придётся искать дыры самим. Прецедент предшественника (Vale) показывает, что
модель памяти меняла фундамент дважды, прежде чем стабилизироваться.

При этом код `symphony/groupify_function.rs` (1896 строк) и
`symphony/check_usages.rs` (691 строка) — возможно, самая ценная вещь,
доступная из Valen: не идеи из статей, а конкретная реализация path-based
группировки и обратного обхода со всеми мелкими подводными камнями, о которых
в статьях не пишут. План MVP стоит строить так, чтобы наш упрощённый вариант
сверялся с Symphony как с эталоном.

## 2. «Нет GC» не значит «нет накладных расходов»

Ovadia написал отдельную статью про миф нулевой стоимости безопасности
памяти. Реальные расходы Keel: bounds-check массивов, рантайм-проверка
generational references там, где статика не справилась, память на хранение
путей для диагностики заимствований. Честная формулировка: расходы
предсказуемы и малы, но не нулевые.

## 3. Безопасность только внутри одной функции

Решение v0 ради простоты анализа (правило 3.7): ссылки не хранятся в полях
структур и не живут дольше функции. Цена: любая долгоживущая структура
(граф, дерево, кэш с обратными ссылками, пул соединений) пишется через
индексы или `Gen<T>`, а не через прямые ссылки. Это ровно то ограничение,
которое вытолкнуло Rust-игры в ECS. Для обработки запроса терпимо, для
состояния сервера — та же «возня с индексами», которую ругали в Rust.

## 4. Грубая инвалидация против точных аннотаций

Инвалидация по пути — консервативное приближение. `mut(self)` на весь объект
убивает все ссылки внутрь, даже если функция трогает одно поле из двадцати.
Точность требует расписывать мутацию по конкретным путям — а это
аннотационная возня, от которой уходили. Компромисс неустраним: простые
сигнатуры дают больше ложных отказов, точные — утяжеляют синтаксис.

## 5. Нет формальной верификации

У borrow checker'а Rust есть доказательство корректности (Stacked Borrows /
Tree Borrows) и десятилетие адверсариального тестирования. У group borrowing
нет ни того, ни другого. Риск пропустить реальный use-after-free реален, и
всплывёт он не на этапе дизайна.

## 6. Компиляция в C ограничивает оптимизации

C как целевой язык не выражает «два изменяемых алиаса безопасны».
`noalias`/`restrict`, которые group borrowing мог бы дать LLVM, через
читаемый C теряются; `tcc` их не поддерживает вовсе. Быстрая dev-сборка и
потенциал производительности в release конкурируют за одно архитектурное
решение, и выбрана скорость сборки. «Производительность вторична» — реальная
цена бэкенда, не формальность.

Смягчение: лёгкий интероп с C (см. дизайн-документ, раздел 6) позволяет
вынести горячий участок в C с `restrict` руками, не таща LLVM в основной
путь компиляции.

## 7. Экосистема с нуля

Ни стандартной библиотеки, ни пакетов, ни сокетов, ни HTTP. Веб-сервер
означает: сначала язык, потом runtime, потом HTTP-парсер, потом TLS через
FFI. Для цели «написать веб-сервер» это порядка 90% работы, borrow checker —
10%.

## 8. Диагностика ошибок решает всё

«Invalidated somewhere ten calls deep» без показа цепочки инвалидации
превращает простой синтаксис в непонятные ошибки и убивает всю ценность
«проще Rust». Rust десятилетие вкладывался в сообщения об ошибках
заимствований. Качество диагностики — не полировка, а условие, при котором
язык вообще пригоден.

## 9. Подтверждено и опровергнуто MVP (2026-11)

MVP-реализация (`/home/ra/keel`) проверила часть рисков на практике.

**Подтвердилось:**

- Пункт 4 (грубая инвалидация) — реален и заметен. `mut(world.entities[])`
  инвалидирует у вызывающего ссылки на все элементы; более точный контракт
  ломается при переходе к грубому. Это ровно та цена точности, о которой
  шла речь.
- Пункт 8 (диагностика) — подтвердился сразу. Сообщения перечисляют пути,
  но не показывают цепочку инвалидации. Для «простого синтаксиса» это
  пока главный дефект.

**Опроверглось (в хорошем смысле):**

- Пункт 2 («нет GC = нет накладных расходов») — на практике проверка
  заимствований в MVP не дала ощутимых накладных расходов: проверка
  выполняется один раз за функцию, в рантайме лишних проверок нет вообще.
  Но это пока масштаб MVP, а не язык целиком.
- Главное противоречие из конца документа («ослабляем ограничения — значит
  придётся доказывать больше») на практике не проявилось: правило
  «инвалидировать ссылки внутри пути» оказалось простым. Плата
  предсказуемость и оказалась в другом месте — в точности контракта и в
  диагностике.

**Новый риск, обнаруженный в MVP:**

- **Проверщик обязан быть детерминированным.** Первая версия искала
  владельца пути обходом `HashMap` и выдавала разные результаты при разном
  seed. Нашлось только потому, что тесты гонялись в двух окружениях
  (Windows и WSL). Класс ошибок: «иногда компилируется, иногда нет» —
  худший вид ошибок в компиляторе, потому что он невоспроизводим.
  Общее правило: любой выбор «один из нескольких равноправных» разбивается
  по стабильному идентификатору.

## 10. Главное противоречие

Хочется одновременно: новую непроверенную модель безопасности, быструю
компиляцию без тяжёлого анализа и синтаксис без аннотаций. Group borrowing
ослабляет ограничения Rust, но ослабление ограничений означает, что
компилятор обязан доказывать больше случаев, а не меньше. Там, где Rust
запрещает («слишком тяжело доказать»), Keel обязуется доказать — и это тянет
анализ в сторону, противоположную приоритету быстрой сборки. Каждое
смягчение ограничения — явный обмен «чуть медленнее компилировать» на «чуть
удобнее писать», а не бесплатное улучшение.
